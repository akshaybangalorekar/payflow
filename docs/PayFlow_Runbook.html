PayFlow Runbook

A runbook is the operational reference for a system: the commands you actually run, what each one does, and what to watch for. It's a real industry artefact — every production service should have one, and being the person who wrote it is a good look.

Where you are: two services and two databases, running as four containers. Accounts is published on your Mac at 18081, transactions at 18082. Inside the container network they are still 8081 and 8082.

SECTION 1Running the stack

These four cover ninety percent of your day.

docker compose -f docker/compose.yml up --build

Build the images and start everything. --build forces a rebuild; without it Docker reuses whatever image it already has, which is the classic reason a code change appears to do nothing. Run after any change to Java code, a pom, or a Dockerfile.

docker compose -f docker/compose.yml up -d

Start in the background ("detached") and give you your terminal back. Without -d, logs stream into the terminal and Ctrl-C stops everything. When you want to work rather than watch.

docker compose -f docker/compose.yml down

Stop and remove all four containers and the network. Your data survives — it lives in named volumes, not in the containers. End of session, or when something is wedged.

docker compose -f docker/compose.yml down -v

The same, plus delete the volumes. Both databases are wiped and Flyway re-runs from scratch on next start. When you want a genuinely clean slate. This destroys your data.

SECTION 2When something is wrong

In order. Don't skip to the bottom.

docker ps -a

Every container and its state. -a includes stopped ones — without it you only see what's running, which hides exactly the container you're debugging. Always the first command. Read the STATUS column.

docker compose -f docker/compose.yml logs transactions

Everything that service printed. Add -f to follow live, --tail=50 for just the end. Whenever a container exits. Find the first "Caused by:" — not the last.

docker exec -it payflow-transactions sh

Open a shell inside a running container. exec runs a command in it, -it makes it interactive, sh is the shell. exit to leave. To check what a container can see from where it stands — files, environment, network.

docker exec payflow-transactions env | sort

Print the container's environment variables. Settles arguments about whether a value actually arrived. When config seems to be ignored.

docker exec payflow-transactions curl -s http://accounts:8081/actuator/health

Test container-to-container reachability from inside. If this works but your Mac can't reach it, the problem is a published port — not the network. When one service can't talk to another.

lsof -nP -iTCP:8081 -sTCP:LISTEN

What on your Mac is holding a port. Built into macOS. A "bind: address already in use" error is always a host-side conflict, so this is always the right tool for it. When a container won't start and the error mentions a port.

Read the STATUS column properly. Up means running · Exited (1) means it started and crashed — go read the logs · Created means it never started at all, which usually means a port clash or a bad mount, and the logs will be empty.

SECTION 3Using the API

Your actual endpoints, from your controllers.

curl -s localhost:18081/actuator/health
curl -s localhost:18082/actuator/health

Is each service genuinely ready? {"status":"UP"} means the app started and its database answers. First thing after any start.

curl -s -X POST localhost:18081/api/accounts \
  -H 'Content-Type: application/json' \
  -d '{"customerName":"Alice","email":"alice@example.com","openingBalance":1000.00}'

Create an account. Returns the account including its generated id — copy it. Setting up test data. Emails are unique; reuse one and you'll get a 409.

curl -s localhost:18081/api/accounts/<ID>

Read one account, including its balance. Before and after a transfer, to prove money moved.

curl -s -X POST localhost:18082/api/transactions \
  -H 'Content-Type: application/json' \
  -H 'Idempotency-Key: demo-001' \
  -d '{"fromAccountId":"<FROM>","toAccountId":"<TO>","amount":250.00}'

Move money. This is the interesting one: it reaches across the container network to the accounts service, then writes a ledger entry to its own database. Send it twice with the same Idempotency-Key — nobody should be charged twice.

curl -s -i localhost:18081/api/accounts/does-not-exist

-i shows the response headers, including the status code. Without it you only see the body, and the status code is often the actual answer. Any time you care whether it was a 404, a 400 or a 502.

SECTION 4Looking in the databases

docker exec -it payflow-accounts-db psql -U payflow -d payflow_accounts

Open a SQL prompt inside the database container. No Postgres client needed on your Mac. To see what's really stored, rather than what the API says.

docker exec -it payflow-transactions-db psql -U payflow -d payflow_transactions

The same, for the transactions database. Remember they are two separate databases — that separation is the whole reason a transfer isn't atomic. To inspect transactions and ledger_entries.

Inside psqlWhat it does
\dtList tables — a fast way to confirm Flyway ran
\d ledger_entriesDescribe one table: columns, types, constraints
SELECT * FROM flyway_schema_history;Which migrations ran, when, and whether they succeeded
SELECT * FROM ledger_entries;Every ledger line. Debits and credits should sum to zero
\qQuit

SECTION 5Housekeeping

docker images

Every image on disk, with its size. Useful for seeing what multi-stage builds actually saved you. Occasionally. Images accumulate.

docker system df

How much disk Docker is using, split by images, containers, volumes and build cache. When your Mac is short on space. Usually the build cache.

docker system prune

Delete stopped containers, unused networks and dangling images. Add -a to also remove images not currently used by a container. Reclaiming space. Volumes are not touched unless you add --volumes.

SECTION 6Git, as used here

git status --short

Which files differ. M modified · D deleted · ?? untracked. Before every commit, and any time someone tells you they changed something.

git diff

Exactly what changed, line by line. Lines starting + were added, - removed, and lines with no prefix are unchanged context. Always. The diff is the truth; a description of a change is not.

git add -A
git commit -m "message"
git push

Stage everything, record it, send it. -A includes deletions, which git add . historically didn't. After each meaningful unit of work — not once a week.

git log --oneline -10

The last ten commits, one line each. Orienting yourself after time away.
