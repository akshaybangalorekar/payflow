GitHub Actions

The robot that builds and tests every push. Arrives in Stage 5 — the concepts now, the hands-on later.

What & why

GitHub Actions is GitHub's built-in automation runner: any YAML file in .github/workflows/ becomes a robot that reacts to events (push, pull request, a schedule) by running commands on a fresh virtual machine. The discipline it enforces is called CI — continuous integration: every push gets built and tested on a clean machine, automatically, with no "works on my Mac" escapes. Red build = no merge. That's the entire religion.

Anatomy — the workflow we will actually write
.github/workflows/accounts-ci.yml
----------------------------------------
name: accounts-ci            # shows up in the Actions tab

on:                          # WHEN to run
  push:
    paths: [ "services/accounts/**" ]   # only when this service changed
  pull_request:

jobs:
  build:
    runs-on: ubuntu-latest    # a fresh VM, every single run
    steps:
      - uses: actions/checkout@v5          # clone the repo
      - uses: actions/setup-java@v5        # install a JDK
        with:
          java-version: '25'
          distribution: temurin
      - run: mvn -B test -f services/accounts/pom.xml   # the point of it all

Vocabulary: trigger (the on: block), runner (the throwaway VM), step (one thing to do), uses: (run a pre-made action someone published) vs run: (run this shell command).

Three concepts that will matter later

Secrets — credentials live in the repo's Settings → Secrets, referenced as ${{ secrets.NAME }}, never in the YAML file. Same rule as .env: it's a leak if it's in the file. Caching — cache ~/.m2 so the runner doesn't re-download the world every push (the basement, on the robot). arm64 builds — our Macs make arm64 images; the runner builds them natively rather than emulating, which is the difference between a 2-minute and 25-minute CI run. We will hit all three in Stage 5.
