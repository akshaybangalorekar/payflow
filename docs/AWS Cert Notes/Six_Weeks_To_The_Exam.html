The stack, as built

Read from the repository on 21 Sep, not assumed. The build track plans against these facts; the design thread deliberately doesn't — an interviewer won't hand you your own codebase.

Runtime

  • Spring Boot 4.1.1 — current line; most tutorials online are still 3.x
  • Java 25 — virtual threads available
  • Maven, two independent POMs — no parent module

Services

  • accounts — port 8081, owns balances
  • transactions — port 8082, owns the ledger
  • RestClient — synchronous, service to service

Data

  • PostgreSQL 17, two databases — one per service
  • Flyway — schema owned by migrations
  • ddl-auto: validate — Hibernate never writes schema

Added 21 Sep — unverified

  • Dockerfile ×2 — multi-stage, non-root, Maven in the image
  • Actuator — health endpoint for container probes
  • Compose runs all four — databases and both services
  • Not "done" until the build runs green

Still missing

  • No tests — neither service has a single one
  • No CI — nothing runs on push
  • No security — any caller can move any money

The design thread

Four scenarios, one per week, each one a topic that actually gets asked. Both domains are yours: five years in banking payments and fraud, seventeen in carrier-grade telecom. Week 2 in particular is territory almost no other candidate can speak to from experience.

Week 1

Zero trust and partner API access

Case: a bank exposes a collections API to 40 partner agencies and ~500 agent users. Accounts move between agencies. Every action must be auditable.

Authentication versus authorization · object-level authorization and why it is never a token claim · token exchange across a trust boundary · why network position is not identity · time-boxed grants and revocation · the confused deputy.

IAMOrganizations / SCPCognitoIAM Identity CenterAPI GatewayWAFSecrets ManagerKMSCloudTrail
Week 2

Atomicity and race conditions

Case: real-time charging on a telecom network — two sessions debit one balance at the same moment. Then the same problem as a bank payout.

Idempotency on a domain identifier · optimistic versus pessimistic locking · lost updates and TOCTOU · transaction boundaries and what a commit actually guarantees · sagas and compensating actions · why exactly-once is a claim with an asterisk.

RDS / AuroraDynamoDB conditional writesElastiCacheSQS FIFOStep FunctionsDAX
Week 3

Resilience and the numbers

Case: fraud scoring inline on the card authorisation path — 350 transactions per second, p99 under 100 ms, under 0.1% timeouts.

RTO versus RPO · multi-AZ versus multi-region and what replication actually costs you · circuit breakers, bulkheads, load shedding · SLI, SLO and error budgets · capacity arithmetic stated as assumptions and sanity-checked.

ALB / NLBRoute 53CloudFrontAuto ScalingECS FargateLambdaCloudWatchX-Ray
Week 4

Events and streaming

Case: fraud, reporting and analytics all need arrangement events in near-real time, from one producer, without coupling.

Partition keys and the ordering they actually guarantee · consumer groups and rebalancing · a log versus a table, and log compaction · transactional outbox and inbox · replay, duplicates, poison events and DLQs · schema evolution.

The services that actually carry the questions

There are roughly thirty-five services worth knowing and about twenty that carry most of the interview. Depth on these beats a shallow pass over everything — for each one, be able to say what it is for, what it guarantees, and what you would use instead.

Compute

  • ECS Fargate — steady containerised services
  • Lambda — spiky, event-driven, cold starts
  • EKS — when the org already runs Kubernetes
  • EC2 — the baseline you argue against

Networking & edge

  • VPC — subnets, NAT, routing, endpoints
  • ALB / NLB — L7 versus L4, where TLS ends
  • API Gateway — external, managed, throttled
  • PrivateLink — private cross-account access
  • Route 53 · CloudFront — DNS, failover, edge

Data

  • RDS / Aurora — relational, Multi-AZ, failover
  • DynamoDB (+DAX) — key access, conditional writes
  • ElastiCache — hot working set, TTLs
  • S3 — the default answer for objects

Events & integration

  • SQS — durable queue, FIFO variant
  • SNS · EventBridge — fan-out and routing
  • MSK / Kinesis — the durable ordered log
  • Step Functions — orchestration and sagas

Identity & security

  • IAM · Organizations / SCP — the real boundary
  • Cognito — customer identity
  • IAM Identity Center — workforce identity
  • KMS · Secrets Manager — keys and rotation

Operations

  • CloudWatch — metrics, alarms, logs
  • X-Ray — tracing across services
  • CloudTrail · Config — audit and detection

The rule this whole plan rests on

Everything in PayFlow so far has been built with help. That is a perfectly legitimate way to learn — it is how the rebalancer went, and that worked. The risk is different: guided building feels like progress and produces a repository, and a repository is not knowledge.

"this is not cold.. this is fully assisted.. i dont know any of this" — 20 Sep

So every build task gets a verification entry, tested in a later session and in a different context. Teaching and testing never happen in the same sitting. Nothing reaches the resume until it survives that. Saying so plainly was the right call, and it is the reason this plan has a check step where the previous one didn't.
