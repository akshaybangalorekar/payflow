AWS for Interviews: the whole picture

Sixteen services grouped into six jobs. A real-time API built end to end. Event-driven architecture built twice — once for events arriving from outside your organisation, once for events from inside — with the security at every hop. Ten trade-offs. Three to four hours, start to finish, and nothing assumes you have used any of it before.

What this book is, and what it is not. It is a single, self-contained read. You do not need another document open beside it, and you do not need to have done the exercises. Everything is explained where it appears. Where a subject has more depth than an interview needs, there is a pointer to the book that covers it — you can safely ignore every one of those pointers on the first read.

One term cleared up immediately, because it has been used at you without explanation. A landing zone is just the AWS setup that exists before any application does — which AWS accounts you have, how their networks connect, and what rules stop people doing damage. Think of it as the building, the wiring and the locks. The applications are the tenants who move in later. Section 6 explains it properly in about ten minutes, and that is all you need for an interview.

SECTION 1Six jobs, sixteen services

↑ contents

There are hundreds of AWS services. You need sixteen, and the way to hold them is not as a list but as six jobs that every system has to do. Once you know the six jobs, any question becomes "which job is this, and which of the two or three candidates fits?"

How to read the last column in the tables below. "What you give up" means exactly that — the thing you lose by choosing this service, and what that loss costs you in practice. Every service in AWS is good at something and bad at something else, and a candidate who names a service without naming what it costs has said nothing. The last column is the half most people never learn.

Job 1 — Let traffic in

ServiceWhat it is, plainlyUse it whenWhat you give up
CloudFront
+ WAF		 CloudFront is a network of servers around the world that sits in front of your system, so users connect to something close to them. WAF is a filter that sits on it and blocks obviously bad requests — known attack patterns, floods from one address, traffic from countries you don't serve. Users are spread out geographically, or you want a filter and a single place to terminate encryption before traffic reaches your Region. You add a caching layer, so you now have to decide how long each thing may be served stale. And WAF only inspects traffic — it can block a known attack pattern or a flood, but it cannot tell whether this particular user is allowed to see this particular record. That check stays in your code, always.
API Gateway A managed front door for APIs. It checks the caller's token, applies a rate limit per customer, validates the request shape, and only then passes it on. The caller is one you do not control — a partner, a mobile app, the public. One more stop on the way in, which adds a few milliseconds to every request. You also pay per request, so on a high-volume internal API the bill grows faster than you'd expect.
ALB
Application Load Balancer		 Spreads incoming requests across your running containers, and routes by path or hostname. The caller is one you control — another of your own services — or you already check the caller's identity yourself. It only spreads traffic across your containers. It will not cap how fast a caller can hit you, will not check the request is well-formed, and has no per-customer keys. If you need any of that, you write it yourself.

The three things API Gateway does that ALB does not. They are named constantly and rarely explained.

Rate limiting — a cap on how many requests one caller may send in a period, say 100 a second. Past the cap, further requests are refused with a "too many requests" response. It protects you from a partner whose retry loop has gone wrong, and from one noisy customer starving everyone else.

API keys — an identifier each caller sends with every request so you can tell them apart, count their usage and bill them. An API key is identification, not security. It says which customer this is; it does not prove they are who they claim, and it decides nothing about what they may see. Proving identity is the token's job.

Request validation — checking the shape of the request before your code ever runs: required fields present, numbers actually numbers, body not oversized. It means malformed input is rejected at the door instead of becoming an exception somewhere deep in your service.

The distinction to say out loud. "API Gateway when the caller is one I don't control, because I want throttling, token validation and request validation without writing them. ALB when the caller is one of my own services, because I won't spend a hop and a per-request charge on features I don't need."

Do not say "inside the network" when you mean "trusted". ALB versus API Gateway is not about inside or outside the network — it is about whether you control the caller. An internal service can be compromised, misconfigured or simply buggy, and treating the internal network as trusted is the assumption that turns one breach into a bad afternoon. Choosing ALB means you have decided to enforce those controls somewhere else, not that you have decided they are unnecessary.

Job 2 — Run my code

ServiceWhat it is, plainlyUse it whenWhat you give up
Lambda You give AWS a function. It runs when something triggers it and costs nothing in between. Nobody is waiting for the answer, and the work is idle most of the day. A nightly file arriving. An event needing enrichment. After a quiet spell the first request waits while AWS starts a fresh copy of your code — for Java that is seconds, and a customer feels it. It also stops at 15 minutes, and nothing survives between calls, so a database connection is opened fresh every time instead of being reused.
ECS Fargate You give AWS a container. It runs continuously. You never touch a server. A long-running service with steady traffic and a latency target. The default for a Spring Boot application, and the right answer far more often than it is given. You pay for it even when it is doing nothing. And adding capacity is slow: from load rising to a new container actually serving traffic is two to five minutes, so a sudden spike hits you well before the extra capacity arrives.

Two more you should be able to name without deep-diving: EKS is managed Kubernetes, correct when the organisation already runs Kubernetes and expensive when it does not, because it needs a platform team permanently. EC2 is a plain virtual machine, correct when you need the operating system itself, a GPU, or a software licence tied to a host.

The distinction to say out loud. "Two questions decide compute: is anyone waiting for the answer, and is it idle most of the day. Lambda when nobody is waiting and it's mostly idle. Fargate when a customer is waiting, because a cold start on a payment screen is a complaint, not a trade-off."

Job 3 — Store state

ServiceWhat it is, plainlyUse it whenWhat you give up
Aurora
PostgreSQL		 A normal relational database, run by AWS, with automatic backups and read-only copies. Tables, joins, transactions, SQL. You need transactions across rows, referential integrity, or the ability to answer a question nobody has asked yet. Every ledger starts here. Only one machine accepts writes. You can add read-only copies to take more reading, but the only way to take more writing is a bigger machine — and eventually there is no bigger machine.
DynamoDB A key-value store. You give it a key, it gives you back a record, in single-digit milliseconds, whether you have a thousand records or a billion. You can write down every query today and in eighteen months. Idempotency keys, session state, feature lookups. You shape the table around the questions you already know you'll ask. A question you didn't plan for is expensive: read the entire table, add a new index, or restructure the data. Reporting and ad-hoc analysis cannot run here at all.
ElastiCache Memory you can share between your servers. Reading from it takes microseconds instead of milliseconds. The same small piece of data is read far more often than it changes — a fraud score, a rate-limit counter, a session. It can drop your data at any moment, so it can never be the only copy. Every item needs an expiry, every read needs code for "it wasn't there", and a value you forgot to clear turns up later as a customer seeing something wrong.
S3 Somewhere to put files. Cheap, effectively unlimited, and extremely durable. Anything that is really a file — statements, settlement files, documents, backups, the raw layer of a data platform. It holds whole files, not rows. You cannot change two files as a single all-or-nothing update, and answering "find me the records where X" needs a separate query tool sitting on top.

The most common wrong answer in interviews. Choosing DynamoDB because the volume sounds large. Volume is not the test — knowing every query is the test. A ledger whose access patterns are still being discovered belongs in Aurora at any volume, and you move the parts that stabilise later.

Job 4 — Move events

This family produces more bad answers than any other, because four services sound interchangeable and are not. One question separates them: does anyone need to read this again later?

ServiceWhat it is, plainlyUse it whenWhat you give up
SQS A to-do list. A worker takes an item, does it, says done, and the item is deleted. Work needs doing once, by one worker, and nobody needs the history. Retries and a failure queue come free. Once a worker finishes an item it is deleted — no history to go back to, and no second reader can ever see it. Messages can also arrive out of order, unless you pick a FIFO queue, and even then order only holds within one group you nominate.
SNS A megaphone. One message, delivered immediately to everyone subscribed. Several systems all need to know the same thing right now, and one of them failing must not affect the others. It stores nothing. A subscriber that happened to be restarting simply never received the message, and there is no way for it to ask again.
EventBridge A sorting office. It looks inside the event and decides where it should go, based on rules you write. Loosely-coupled services where the routing rule should live in the bus, not hard-coded in the producer. It decides where an event goes and then forgets it. No history, no guaranteed order, and you pay for every event that passes through.
Kinesis
or MSK		 A diary. Every event is written down and kept for a set period — seven days, a year — and any number of readers go through it at their own pace, each with their own bookmark. Anyone might need to read it again: a new consumer next year, a bug fix that needs reprocessing, an auditor. MSK is Kafka; Kinesis is the AWS-native equivalent. Order only holds inside one lane, called a partition. So the field you route by decides two things at once: what stays in order, and how many consumers can work in parallel. It is hard to change later, and that decision is now yours.

Say this and you will impress a panel. "This doesn't need a log — one producer, one consumer, no replay. SQS." Being able to rule Kafka out is a stronger signal than knowing Kafka, because reaching for Kafka where SQS fits is the most common over-engineering mistake in the industry.

Job 5 — Prove who you are

ServiceWhat it is, plainlyUse it whenWhat you give up
IAM How your software proves what it is to AWS. A container is given a role, and credentials arrive automatically and expire automatically. Always. This is how every piece of your software talks to every AWS service. Nothing, used properly. One hard rule: never put a long-lived access key in an application. An access key is a password that never expires, and it is where most cloud breaches start.
Cognito How your customers sign in. Sign-up, sign-in, password reset, and it issues a token your API can check. You have end users and don't already have an identity system for them. It only handles your customers. Your staff need a different service (IAM Identity Center), and your software needs IAM — so you end up running three separate identity systems and having to keep straight which is which.
KMS +
Secrets Manager		 KMS holds encryption keys and records every single use of them. Secrets Manager holds passwords and rotates them on a schedule. Any data an auditor cares about, and any credential your application needs. Turning encryption on is the easy part, and it is not the part anyone asks about. The work is deciding who may decrypt and keeping the record of who did — and that is a key policy plus CloudTrail, not a checkbox.

Job 6 — Know what happened

ServiceWhat it is, plainlyThe architect's point
CloudWatchMetrics, logs and alarms.Alarm on things customers feel — error rate and latency against your target. Alarming on CPU produces noise and misses real outages.
X-RayFollows one request across several services and shows where the time went.Without it, "the payment took nine seconds" has no answer. The request id must cross every boundary, including queues, or the trail stops exactly where the problem is.
CloudTrailRecords every AWS API call: who, what, when.This is the evidence a regulator asks for. On in every account from day one, and written somewhere nobody can delete it.

If you are asked how many AWS services you know

"About sixteen properly, grouped by the job they do, and I can argue each against its alternatives. Past that I know what exists and I'd look it up — which is what I'd do on the job anyway."

That answer is stronger than a list of ninety names. A panel is measuring judgement, not recall, and a candidate who names a service without naming what it costs has said nothing.

SECTION 2A real-time API, built end to end

↑ contents

First, what "real-time" actually means

The phrase is used for two completely different things, and mixing them up is an early credibility loss.

 Real-time APIReal-time streaming
ShapeSomeone asks a question and waits for the answer.Events flow continuously and are processed as they arrive.
Example"Is this card transaction fraudulent?" — the terminal is waiting."Update the fraud model's view of this customer" — nobody is waiting.
Measured byResponse time, at a percentile. "p99 under 100 milliseconds."Lag — how far behind the consumer is.
Built fromAPI Gateway or ALB → Fargate → cache → database.Kinesis or MSK → consumers. Section 4.

When someone says "real-time API", they mean the first one, and they mean it has a latency budget: a number of milliseconds inside which the whole thing must finish, measured at a percentile rather than an average.

Why percentiles, not averages. "Average response time 40 milliseconds" can hide the fact that one request in a hundred takes four seconds. p99 means 99 out of 100 requests finish inside the number. At a million requests a day, the slowest one percent is ten thousand unhappy customers, so that is the number the business actually feels. Always state your target as a percentile.

The scenario we will build

Card fraud decisioning. When a card is swiped anywhere in Australia, the payment switch calls your API and asks: approve or decline? It will wait 100 milliseconds and no longer — after that it times out and applies its own default. Peak is 350 requests per second, and it runs 24 hours a day. Getting it wrong costs money in both directions: a wrong decline is an angry customer, a wrong approve is a loss.

Where the 100 milliseconds goes

This is the single most useful habit in a latency-sensitive design: spend the budget on paper before you draw anything. It tells you immediately which options are available to you.

StepBudgetWhy
Network in from the switch~10 msNot yours to control. Assume it and move on.
Load balancer~2 msAn ALB adds very little. An API Gateway would add more — which is one reason it is not used here.
Your service: parse, validate, authorise~5 msCheap, and it must happen.
Fetch the customer's features~15 msThe expensive step. From cache it is about 1 ms; from the database, 15 to 25 ms. This is where the design happens.
Score the transaction~20 msA model evaluation. In-process is fastest; a separate endpoint adds a network hop.
Write the decision~0 msZero, because you do not write on the critical path. You emit it and move on — see below.
Response back~10 msSame as inbound.
Total~62 msLeaving ~38 ms of headroom. You need it: garbage collection pauses, a slow cache node, a retry.

The move that wins this design. Notice the "write the decision" row costs zero. The decision must be recorded — for disputes, for audit, for training the model — but nobody is waiting for that write. So it goes onto a stream and happens afterwards. Everything that is not the decision comes off the path. That sentence is the answer to this whole question.

The design

1
THE PAYMENT SWITCH

The caller is inside the bank, over private connectivity rather than the public internet, and it presents a client certificate (mutual TLS) so you know which machine is calling.

Note what mTLS does and does not do: it authenticates the connection, not the request. It tells you the switch is calling. It says nothing about which customer or which card, and it is not authorisation.
2
ALB, NOT API GATEWAY

This is the first real decision. The caller is internal and trusted, there is no partner to rate-limit, and every millisecond is spoken for. API Gateway's throttling, API keys and usage plans buy you nothing here and cost you latency and per-request charges.

Reverse this for an external caller. Section 3 uses API Gateway for exactly that reason.
3
FRAUD SERVICE · ECS FARGATE

Fargate, not Lambda, and the reason is one word: cold start. A 100 ms budget leaves no room for AWS to start a fresh copy of a Java application, and the traffic never drops to zero, so Lambda's "pay nothing when idle" saves nothing here.

The container runs in a private subnet with no inbound route from the internet. It gets its permissions from an IAM role — there is no access key anywhere in the image or the configuration.
4
ELASTICACHE — THE HOT PATH

The features the model needs — how many transactions this card made in the last hour, the customer's usual merchant categories, their typical amount — are read on every single request and change slowly. In memory, that read is about a millisecond.

Every cached value needs an expiry, and every read needs a plan for a miss. A cache that silently returns yesterday's velocity counter will approve a fraud pattern it was built to catch.
5
DYNAMODB — WHEN THE CACHE MISSES

The durable feature store. One key — the card or customer identifier — one record, single-digit milliseconds, at any volume. This is DynamoDB's best possible fit: you know the only query, and it will never change.

If the cache is empty after a deployment, every request goes here at once. Size for that, and warm the cache deliberately rather than hoping.
6
SCORING, IN-PROCESS

The model runs inside the same container. A separate endpoint would be cleaner to operate and would add a network hop you cannot afford.

The cost is that shipping a new model means shipping a new container. That is a real operational trade-off and you should name it rather than pretend it away.
7
EMIT THE DECISION — FIRE AND FORGET

The decision goes onto a Kinesis stream and the service moves on without waiting for anything downstream. Case management, the dispute system, the analytics platform and the model training pipeline all read that stream at their own pace.

This is the design move. Writing to Aurora here would add 20 ms and, worse, would mean a database slowdown becomes a fraud-decisioning outage.
8
AURORA · ISOLATED SUBNET

A separate consumer reads the stream and writes decisions into Aurora, where analysts and the dispute process need joins and ad-hoc queries. It sits in a subnet with no route out to the internet at all.

That last point is a real control: a compromised database host cannot call an attacker's server, because there is no route for it to use.
9
↩ BACK TO THE SWITCH

Approve or decline, in roughly 62 milliseconds, with 38 to spare.

The capacity arithmetic, in five minutes

Interviewers ask for this and most candidates either skip it or drown in it. Keep it to three numbers and state your assumptions out loud.

How much concurrency?

concurrency = throughput × how long each request takes = 350 per second × 0.062 seconds

≈ 22 requests in flight at any one moment

How many containers?

22 concurrent ÷ 50 each container handles comfortably = 1 container

Real answer: 3 — one per availability zone

Resilience set that number, not throughput. One container cannot survive losing a zone, and at three you are running at about a third of capacity, which is the headroom that absorbs a spike. Say this out loud in an interview: it is the difference between arithmetic and design.

How many database connections?

only cache misses reach DynamoDB, at a 90% hit rate 350/s × 10% = 35 reads per second, at ~8 ms each concurrency = 35 × 0.008

≈ 0.3 — trivial

The cache is doing the heavy lifting. If the hit rate falls to 50% that becomes 175 reads a second — five times the load, from one number moving. So the cache hit rate is worth alarming on, and it is the figure to quote when someone asks what you would monitor.

And in two years?

3× growth → 1,050 per second → ~65 concurrent

Still small

The first bottleneck is not throughput at all. It is the cache hit rate and the tail latency of the scoring step. Naming the bottleneck the numbers did not reveal is the move that separates a senior answer from a correct one.

figure 4 — the shape of the answer matters more than the precision

The line that lands here. "Throughput isn't my constraint at this scale — three containers cover it and I only have three because I want one per availability zone. My constraints are the cache hit rate and the tail latency of the scoring step, and those are what I'd measure and alarm on."

Security, at every hop

HopWho is proving whatHow

The sentence that separates an architect from an enthusiast. mTLS, a security group and a private subnet all tell you where a request came from. None of them decides whether this caller may see this record. That check — called object-level authorization — happens in your code, on every query, or it does not happen. It is the most common serious API vulnerability in the industry.

The 60-second version, for an interview. "Latency is the product here, so I start by spending the budget on paper. The switch is internal, so ALB rather than API Gateway — I won't pay a hop for throttling I don't need. Fargate rather than Lambda, because a cold start doesn't fit in 100 milliseconds. Features come from ElastiCache with DynamoDB behind it, because that read is the expensive step and I know the only query. The decision is emitted to a stream and written to Aurora by a separate consumer, so a database slowdown can never become a decisioning outage. Three containers across three zones — resilience sets that number, not throughput. And my real constraints are cache hit rate and the tail of the scoring step, which is what I'd alarm on."

SECTION 3Event-driven — events from outside your organisation

↑ contents

What event-driven means, plainly

In a request-driven system, service A calls service B and waits. A knows B's address, A knows B's contract, and when B is down, A is broken.

In an event-driven system, A announces something that happened — payment.completed — and stops caring. B, C and D read it if they are interested. A does not know they exist. B can be down for an hour and catch up afterwards.

That is the whole idea. Banks use it because their systems are owned by different teams on different release cycles, and because regulators like a durable record of what happened.

What it costs, which you must say too. You lose the immediate answer — the publisher does not know whether anything worked. You gain a schema that several teams now depend on, so it has to be governed. And every message can arrive twice, which is discussed below and is not optional to handle.

The scenario

A payments partner sends you events. A fintech that originates payments on your rails needs to tell you about each one. Peak 2,000 events per second. Their events must reach six internal consumers. You must be able to prove, two years later, exactly what they sent and when. Three more partners join next year.

The question that decides the whole design

Do you give the partner a Kafka client and let them publish directly to your topic?

It is tempting. It is fewer moving parts, it is lower latency, and the partner's engineers will ask for it. The answer is no, and being able to say why in three sentences is a strong interview moment.

Give the partner Kafka directlyPut an API in front
They need network access into your estate.They call an HTTPS endpoint. No network access at all.
A malformed message lands in your topic and every consumer has to deal with it.Rejected at the edge, with a 400 and a reason. Your topic stays clean.
Throttling a misbehaving partner means Kafka quotas, and the bad traffic has already arrived.A usage plan per partner. The flood stops outside.
Their credential is a Kafka principal — a thing your identity team does not manage.An OAuth client, issued and revoked by your normal process.
Changing your topic layout is now a breaking change for an external company.The API is the contract. The topics stay yours to reshape.
Every new partner is a networking project.Every new partner is a client registration.

Say this out loud. "I'd never expose Kafka to a partner. I'd put a controlled API in front of it. That gives me authentication I already manage, validation before anything reaches my topic, per-partner throttling, and it keeps my topic design as an internal concern rather than a contract with an external company. The API is the boundary; the log is internal plumbing."

The design

1
THE PARTNER

Their system exchanges a client id and secret for a short-lived token — this is the OAuth client credentials flow, which is what a system uses when there is no human to log in. The token carries scopes and an expiry.

Why not just an API key? A key identifies a caller but carries no scopes, no expiry and no clean revocation story. In practice you use both — the key for the usage plan, the token for identity.
2
CLOUDFRONT + WAF

Blocks known attack patterns, rate-limits by source address, and terminates encryption before traffic reaches the Region.

WAF reduces noise. It has never made an authorisation decision and never will.
3
API GATEWAY

Validates the token, applies this partner's throttle, and checks the body against a schema. A malformed event is rejected here with a 400 explaining why.

This is the difference between a bad partner release being their incident and it being yours.
4
INGESTION SERVICE — WHERE IDENTITY CHANGES HANDS

The most important step in this design. The partner's OAuth identity stops here. Everything downstream runs under the ingestion service's AWS IAM role. The service must therefore carry the partner's identity forward as data on the event, because AWS has no idea who the partner is.

Get this wrong and you have a confused deputy — a powerful internal service acting on a request without remembering whose request it was. Tenant attribution is lost, and every downstream consumer now trusts an event it cannot attribute.
5
DYNAMODB — IDEMPOTENCY

The partner's Idempotency-Key is written with a conditional write: create this only if it does not already exist. If it exists, you return the stored response instead of processing again.

Their network will time out and they will retry. Without this, one payment instruction becomes two payments — which in banking is a remediation programme, not a bug.
6
WRITE TO THE LOG

Only now does the event enter the stream, validated, attributed, and de-duplicated.

7
PRIVATELINK BETWEEN ACCOUNTS

The ingestion account reaches exactly one endpoint in the streaming account. The two networks are never joined.

If you peered the networks instead, you would be telling a security review that an internet-facing account has a route into the account holding the event backbone. Those are very different conversations.
8
THE LOG · PARTITIONED BY PAYMENT ID

Order is only guaranteed within a partition, so the field you partition by is also your parallelism limit. Payment id keeps each payment's events in order while letting different payments process simultaneously.

A schema registry enforces backward compatibility, which is what lets six consumers upgrade independently instead of in lockstep.
9
ARCHIVE TO S3

Seven-year retention belongs in object storage, not broker storage, at roughly a tenth of the cost. Written to a bucket nobody can modify or delete from.

"Prove what they sent two years ago" is a requirement, and this is the only affordable way to meet it.
10
↩ 202 ACCEPTED

The partner gets an immediate acknowledgement meaning received and durably stored — not processed. Being precise about that distinction in an interview is worth a lot.

The three identities — the thing panels probe hardest

One partner event involves three completely different identities, issued by three different systems, living for three different lengths of time. Candidates who blur them get found out quickly.

IdentityWho issues itLives forWhat it provesWhere it stops
Partner OAuth clientYour authorisation serverMinutesWhich partner organisation is callingAt API Gateway and the ingestion service. It goes no further.
Ingestion service IAM roleAWSAn hour, rotated automaticallyWhich of your workloads is actingInside AWS only. It says nothing about the partner.
Stream principalMSK via IAM, or a Kafka credentialVariesWhich client may write to which topicAt the broker. It authorises the topic, not the business action.

The consequence, and the sentence to remember. Because the partner's identity stops at the edge, the tenant must travel on the event as data — and every consumer must use it. Otherwise the ledger consumer processes an event with no idea which partner it came from, and you have both lost attribution and created a path where one partner's event could affect another's data.

Say this out loud. "There are three identities here and they're not interchangeable: the partner's OAuth client at my edge, my ingestion service's IAM role inside AWS, and the stream principal at the broker. Different issuers, different lifetimes, different enforcement points. The partner's identity stops at the edge, so tenant has to travel on the event and every consumer has to honour it — otherwise I've built a confused deputy."

SECTION 4Event-driven — events from inside your organisation

↑ contents

Now the other direction. Your own payments service needs to publish payment.completed so that fraud, the ledger, notifications and analytics can react. Everything is inside your own AWS organisation.

It sounds easier. In one specific way it is much harder, and that is where the interesting question lives.

The hard part: the database and the broker are two different systems

Your payments service does two things: it writes a row to its database, and it publishes an event. There is no way to make those one atomic operation, because they are two separate systems. So one of two bad things can happen.

The answer: the transactional outbox

Write the business row and a "message to be sent" row in the same database transaction. Either both exist or neither does — that is what a transaction guarantees. Then a separate process reads the outbox table and publishes.

The honest sentence about exactly-once. The outbox does not give you exactly-once delivery. Nothing does. The relay can publish an event and crash before recording that it did, so it publishes again. What you get is at-least-once delivery with no lost events, and exactly-once effect is then built in the consumer — a unique key, a conditional write, or a natural business identifier the consumer checks before acting.

Saying "Kafka gives you exactly-once" is a common and costly answer. Saying "delivery is at-least-once, so exactly-once has to be an effect I build" marks you out immediately.

Security for internal events — and why "internal" is not a security model

The temptation with internal events is to relax, because it is all inside your own network. That instinct is precisely what zero trust exists to correct. The network tells you where a request came from; it tells you nothing about whether it should be allowed.

QuestionAnswer for an internal producer or consumer
Who is this workload?An IAM role on the Fargate task. With MSK you can use IAM authentication, which means the same identity that reads S3 also writes to the topic — one identity system, one audit trail. The alternatives are SASL/SCRAM credentials or mutual TLS certificates.
What may it do?Authorisation is per topic and per consumer group, not per cluster. The payments service may write to payments.* and nothing else. The fraud consumer may read that topic, in its own consumer group, and write nowhere.
How does it reach the broker?Privately. MSK brokers sit as network interfaces in your own subnets; nothing is exposed to the internet. Cross-account access goes over PrivateLink rather than joining networks.
Is the data protected?Encrypted in transit between clients and brokers and between brokers, and at rest with KMS — with a key policy naming who may decrypt and CloudTrail recording every use.
Who did what?CloudTrail for the AWS control plane, broker logs for produce and consume activity, and the S3 archive as the durable record of the events themselves.
What if a consumer is compromised?It can read the topics its role allows and nothing else. It cannot write. It is in its own AWS account, so the blast radius stops at that account boundary.
What about sensitive fields?Do not put a full card number or personal data in an event that six teams read. Publish a reference and let the entitled consumer fetch the detail, or encrypt the field so only holders of that KMS key can read it.

Say this out loud. "Internal doesn't mean trusted. Each producer and consumer has its own IAM role, authorisation is per topic and per consumer group rather than per cluster, connectivity is private, and sensitive fields don't travel in an event six teams can read. Being on my network is not a permission."

The four things that go wrong, and what you say about each

DuplicatesThe same event processed twice.Expected, not exceptional. Consumers are idempotent by design — a unique key, a conditional write, or a natural business identifier.

The 60-second version, for an interview. "For partner events I put a controlled API in front — OAuth, per-partner throttling, schema validation and an idempotency key — and only validated, attributed events reach the log. The partner never gets broker access, and their identity stops at the edge, so tenant travels on the event. For internal events the atomicity problem is real, so producers use a transactional outbox: the business row and the outbox row commit together and a relay publishes afterwards. That gives me at-least-once with no lost events, so every consumer is idempotent. Authorisation is per topic and per consumer group, connectivity is private, and my primary metric is consumer lag."

SECTION 5Ten trade-offs, with what changes your mind

↑ contents

Each one in three parts: what decides it, the default answer, and what would change your mind. That third part is what a panel is really listening for, because it is the difference between a decision and a preference.

DecisionWhat decides it · the default · what changes your mind
1. Lambda or FargateDecides it: is anyone waiting, and is it idle most of the day.
Default: Fargate for anything a customer waits on.
Changes your mind: nobody waiting and long idle periods → Lambda, and the cold start costs nothing.
2. Aurora or DynamoDBDecides it: can you write down every query, today and in eighteen months.
Default: Aurora, because new questions keep arriving.
Changes your mind: one key, one lookup, never changing → DynamoDB. Volume alone never changes it.
3. API Gateway or ALBDecides it: is the caller inside or outside your trust boundary.
Default: API Gateway externally, ALB internally.
Changes your mind: a tight latency budget on an internal path → ALB even if you would like the gateway's features.
4. Queue or log
(SQS or Kafka)		Decides it: will anyone need to read this again.
Default: SQS, because it is far simpler.
Changes your mind: replay, several independent consumers, or an audit requirement → a log.
5. Synchronous or asynchronousDecides it: is a human waiting, and does the caller need the answer to continue.
Default: asynchronous, because it decouples.
Changes your mind: a customer standing at a terminal → synchronous, because a queued answer is no answer.
6. Cache, read replica, or CDNDecides it: three different problems — the same query repeated, read load on the primary, or distance.
Default: name which problem you have first.
Changes your mind: reads must be current and analytical → a replica, not a cache.
7. Multi-AZ or multi-RegionDecides it: how long you may be down, how much data you may lose, and what the business will pay.
Default: multi-AZ, which covers the overwhelming majority of failures.
Changes your mind: a stated recovery target a single Region cannot meet → multi-Region, and be honest that it is mostly a data problem.
8. Managed or self-managed
(MSK or Confluent, Fargate or EKS)		Decides it: who carries the pager, and whether the vendor boundary is acceptable.
Default: managed, unless you have the team.
Changes your mind: a regulator asking whose account holds the data → keep it in yours.
9. Orchestration or choreographyDecides it: will someone ask "where is payment 4471?"
Default: orchestration for money — Step Functions, with state you can query.
Changes your mind: independent teams who must not queue behind a central component → choreography.
10. Where authorization livesDecides it: nothing. There is only one answer.
Default: in your code, per object, on every query.
Changes your mind: nothing does. No firewall, WAF, security group or gateway has ever decided whether a caller may see a record.

SECTION 6Landing zone, explained in ten minutes

↑ contents

This is the term you said you would not know what to say about. Here is everything an interview actually needs.

What it is

A landing zone is the AWS setup that exists before any application does. Three things:

  1. Which AWS accounts you have, and how they are grouped.
  2. How their networks connect — to each other, to your data centre, to the internet.
  3. What rules stop people doing damage, applied centrally.

The building, the wiring and the locks. The applications move in afterwards.

Why more than one account

Because the AWS account is the only real wall. Everything else — security groups, IAM policies, separate networks — is a wall inside the same building. Five specific consequences:

  • Blast radius. A compromise or a mistake stops at the account edge.
  • Limits are per account. A load test in one team's account cannot exhaust the capacity another team's payment service needs.
  • Billing separates itself, with no tagging discipline required.
  • Permissions become sentences you can verify — "admin in dev, read-only in prod" — instead of hundreds of lines of conditions.
  • The hard ceiling only attaches here. A service control policy, the one thing that can say "nobody in here may do this, ever", attaches to an account or a group of accounts.

Four facts that answer most landing-zone questions

1. Nothing runs in the management account. Service control policies do not apply to it, so anything running there sits outside your strongest control. It is also the account that can alter the organisation itself.

2. A service control policy only ever subtracts. It never grants anything. An action succeeds only if an IAM policy allows it and no policy denies it. It does apply to a member account's root user, which is what makes it a real ceiling.

3. Preventive and detective are different. A service control policy is preventive — the API call fails. AWS Config is detective — the thing gets created and you find out afterwards. Offering Config as the answer to "how would you stop that?" means "I would find out later".

4. A subnet is public because of its route table, not a setting. Public subnets have a route to the internet gateway and hold load balancers. Private subnets route outward through a NAT gateway and hold your containers. Isolated subnets have no outward route at all and hold your database — so a compromised database host cannot call an attacker's server.

Four connectivity answers

NeedAnswerThe catch
Two networks talkVPC peeringNot transitive. Fine for two, unworkable at ten.

Expose one service, not your networkPrivateLinkOne-way. Overlapping address ranges stop mattering. This is the one to reach for with partners and other business units.
Reach the data centreDirect Connect, with a VPN backupDirect Connect is private, not encrypted. If the requirement says encrypted in transit, you still need TLS or a VPN over it. This is a favourite interview trap.

The 45-second version. "A landing zone is the account structure, network and guardrails that exist before any application. I'd use multiple accounts because the account is the only real isolation boundary — blast radius, quotas, billing and IAM all separate in one move. Organise the organisational units by the policy you want to apply, not by the org chart, because reorganisations happen and guardrails don't. Nothing runs in the management account, because service control policies don't apply to it. And I'd start with Control Tower rather than building it by hand."

That is genuinely enough for an interview. Book 02 · Landing zone has the depth — address planning, endpoints, DNS, shared services, the worked bank design and ten more questions — for when you want it. You do not need it today.

SECTION 8Every answer on one page

Read this last, and read it again the morning of an interview. It is only useful once the sections above have landed — on its own it is a list of assertions.

How many AWS services do you know? "About sixteen properly, grouped by the job they do, and I can argue each against its alternatives. Past that I know what exists and I'd look it up — which is what I'd do on the job anyway."

Lambda or Fargate? "Two questions: is anyone waiting for the answer, and is it idle most of the day. Lambda when nobody's waiting and it's mostly idle. Fargate when a customer is waiting — a cold start on a payment screen is a complaint, not a trade-off."

Aurora or DynamoDB? "Can I write down every query today and in eighteen months? If yes, DynamoDB and I model for them. If no, Aurora, at any volume. Volume isn't the test — knowing every query is the test."

API Gateway or ALB? "API Gateway when the caller is outside my boundary, for throttling, token validation and request validation I'd otherwise write. ALB when the caller is one of my own services, because I won't spend a hop on features I don't need."

SQS or Kafka? "Does anyone need to read this again — replay, a new consumer next year, an auditor? If no, it's a queue. If yes, it's a log. Reaching for Kafka where SQS fits is the most common over-engineering mistake there is."

Design a real-time API. "Latency is the product, so I spend the budget on paper first. Internal caller means ALB, not API Gateway. Fargate not Lambda, because a cold start doesn't fit in 100 milliseconds. Cache in front of a key-value store for the expensive read. Everything that isn't the decision comes off the path — I emit and move on. Three containers across three zones, because resilience set that number rather than throughput."

A partner wants to send us events. "I'd never expose the broker. A controlled API in front gives me OAuth, per-partner throttling and schema validation, and keeps my topic design internal rather than a contract with another company. Their identity stops at my edge, so tenant travels on the event and every consumer honours it — otherwise I've built a confused deputy."

The three identities. "Partner OAuth client at the edge, my ingestion service's IAM role inside AWS, and the stream principal at the broker. Different issuers, different lifetimes, different enforcement points. They are not interchangeable and collapsing them is how tenant attribution gets lost."

How do you publish events reliably from a service? "A transactional outbox. The business row and the outbox row commit in the same database transaction, so either both exist or neither does, and a relay publishes afterwards. That gives me at-least-once with no lost events — so every consumer is idempotent."

Doesn't Kafka give you exactly-once? "Delivery is at-least-once. Exactly-once has to be an effect I build — a conditional write on a stable key, with the result stored so a retry returns the same answer."

How do you secure internal events? "Internal doesn't mean trusted. Each producer and consumer has its own IAM role, authorisation is per topic and per consumer group rather than per cluster, connectivity is private, and sensitive fields don't travel in an event six teams read. Being on my network is not a permission."

What's your primary metric for an event-driven system? "Consumer lag. Not CPU. Lag tells me whether the business is falling behind, and the ceiling on fixing it is the partition count — I can't have more active consumers in a group than partitions."

What is a landing zone? "The account structure, network and guardrails that exist before any application. Multiple accounts because the account is the only real isolation boundary. Organisational units named after the policy that applies, not the org chart. Nothing in the management account, because service control policies don't apply to it. Control Tower rather than building it by hand."

How do you stop deployments outside Australia? "A service control policy denying every Region except the approved ones. That's preventive — the API call fails. I wouldn't answer with AWS Config, because Config is detective and only tells me afterwards."

GLOSSARYEvery term used here, in ordinary language

↑ contents

p99 / percentile"p99 is 100 ms" means 99 of every 100 requests finish within 100 ms. Averages hide disasters; percentiles do not. Why it matters: at a million requests a day, the slowest 1% is ten thousand unhappy customers.
Cold startWith Lambda your code is not running until something calls it. If no warm copy exists, AWS must start one first, and that request waits. For Java it is seconds. Why it matters: invisible on a nightly job, a complaint on a payment screen.
Critical pathThe chain of steps somebody is actually waiting on. Recording a decision afterwards is off the critical path. Why it matters: you are allowed to be slow off it, and that is where the cheap options live.
ConcurrencyHow many requests are in flight at the same moment. It equals throughput multiplied by how long each takes. Why it matters: it is how you size containers, threads and connection pools without guessing.
IdempotentDoing it twice has the same effect as doing it once. Setting a balance to $750 is; subtracting $250 is not. Why it matters: every messaging system delivers at least once, so duplicates will happen.
At-least-once deliveryIf the sender gets no acknowledgement it sends again, so you may receive a message twice but you will not lose it. Why it matters: "exactly once" is not something you buy — it is an effect you build.
Idempotency keyA unique identifier the caller puts on a request. You record it and store the response; if it arrives again you return the stored response. Why it matters: it is how a partner safely retries a payment after a timeout.
Transactional outboxWrite the business row and a "message to send" row in the same database transaction, then publish from a separate process. Why it matters: it is the only honest way to make "save and publish" atomic.
PartitionA stream is split into lanes; order is guaranteed only within a lane, and one consumer handles a lane at a time. Why it matters: the field you partition by decides both what stays in order and how much runs in parallel.
Consumer lagHow far behind a consumer is — how many events it has not read yet. Why it matters: it is the primary health metric for anything event-driven, far more useful than CPU.
Dead-letter queueWhere a message goes after failing too many times, so it stops blocking everything behind it. Why it matters: without one you either lose bad messages silently or retry them forever.
Consumer groupCopies of the same application sharing the work of a stream, each group keeping its own position. Why it matters: it is how six teams read the same events independently.
OAuth client credentialsThe flow a system uses to get a short-lived token, as opposed to a person logging in. Why it matters: it gives you expiry, scopes and revocation, which a plain API key does not.
mTLSNormal TLS proves the server's identity; mutual TLS makes the client prove its identity too. Why it matters: it authenticates the connection, not the request — it tells you which machine, not which customer, and it is not authorization.
Object-level authorizationChecking that this caller may see this specific record, not just that they are logged in. Why it matters: no AWS service performs this check. Your code does, on every query, or nobody does.
Confused deputyA trusted service tricked into using its own high privileges for a caller who should not have them. Why it matters: it is what happens when an ingestion service forgets whose request it is acting on.
IAM roleHow a piece of software proves what it is to AWS. Credentials arrive automatically and expire automatically. Why it matters: the alternative is a long-lived access key, which is a password that never expires.
Service control policyAn organisation-wide rule setting the maximum permissions for an account. It only subtracts, never grants. Why it matters: it is preventive — the API call fails — unlike AWS Config, which only reports afterwards.
PrivateLinkExposes one service to a consumer, one-way, without joining the two networks. Why it matters: "we published one endpoint" is a far easier security conversation than "we joined our networks".
Landing zoneThe accounts, networks and guardrails that exist before any application does. Why it matters: in an enterprise engagement it is usually the first thing you are asked to design.
RTO and RPORTO is how long you may be down. RPO is how much recent data you may lose. Both are durations, of different things. Why it matters: people mix them up constantly, and cross-Region replication is asynchronous, so your RPO is never zero across Regions.
Blast radiusHow much breaks, and how many customers notice, when one thing fails. Why it matters: it is the first and best argument for more than one AWS account.
