Why this note exists

The most common opening question in a system design interview is some version of "walk me through what happens when a user does X." Not "what is Docker" — nobody asks that. They ask you to narrate a request through a system and they listen for where you stop being able to.

This note is a worked example of that answer, using a system you built. By the end you should be able to trace one request from a curl command to a row in Postgres and back, naming every boundary it crosses and what each layer decides. That narration is the skill. The Docker facts are the scenery.

Parts eight and nine are the interview half. A panel rarely asks "what does open-in-view do" — they describe a symptom and watch you locate it. Every scenario there is written from the symptom inward, and each ends with the one sentence worth saying out loud.

PART ONEWhy containers exist at all

Before 1956, loading a ship meant dockworkers carrying barrels, sacks and crates aboard one at a time. Every cargo was a different shape, so every ship, truck and warehouse handled it differently. Loading a ship took days.

Then someone standardised the box. Not the cargo — the box. Suddenly it didn't matter whether you were shipping coffee or car parts: the crane, the ship, the truck and the train all handled one standard shape. Loading dropped from days to hours.

Software had exactly this problem. Your app needs Java 25, Maven, a particular Postgres version and a pile of settings. Your laptop has one combination, a colleague's has another, the build server a third, production a fourth. Most deployment failures were some version of "but it works on my machine."

A container is the standard box. Your application and everything it needs to run, sealed into one unit. The machine underneath doesn't need Java installed. It only needs to know how to handle a box.

Say this out loud

"Containers standardise the unit of deployment. The host stops needing to know what's inside — it only needs a runtime that can start a box."

PART TWOImage and container — one distinction

You already know this shape from Java:

   DOCKER                          JAVA
   ──────                          ────
   IMAGE          is like          CLASS
   a frozen filesystem             a template
   sitting on disk, inert          sitting in a .class file, inert
   built once                      compiled once
        │                               │
        ▼                               ▼
   CONTAINER      is like          OBJECT
   a running instance              a running instance
   many from one image             many from one class

figure 1 — the only Docker vocabulary you must never mix up

An image is a frozen snapshot of a filesystem, plus a note saying what to run when it starts: "here is Linux with a JRE installed and a jar at /app/app.jar — run java -jar /app/app.jar."

A container is that image actually running. Start three containers from one image and you get three separate processes with separate memory — exactly like three objects from one class.

Images are built. Containers are run. That's the whole vocabulary.

figure 2 — four containers, two databases, one private network

Stop here. This is the bit that trips everyone.

Notice that transactions reaches accounts at http://accounts:8081 — not localhost:8081. And it reaches its database at transactions-db:5432, not localhost:5433.

Inside a container, localhost means that container itself. Not your Mac, not the other containers. A container is its own little machine with its own network identity.

Compose gives every service a name, and that name works as a hostname on the private network it creates. So accounts, accounts-db and transactions-db are all reachable by name, from any other container in that network.

The only reason 18082 exists at all is so you, standing outside, can get in. That's what ports: "18082:8082" does — host port on the left, container port on the right. Inside the network nobody uses 18082. They all use 8082.

Say this out loud

"Inside the compose network, services address each other by service name. Published ports only exist for traffic entering from outside."

PART FOURThe three files, and the moment each one acts

↑ contents

Alice's $250 moved because three files did three different jobs. They are usually taught together as "the config files", which is the single most confusing thing anyone can say about them. They are not the same kind of thing, they are not read at the same time, and changing one has a completely different blast radius from changing another.

The clearest way to separate them is by when they act.

  ① BUILD TIME — on a build machine, once per commit
  ┌─────────────────────────────────────────────────────────────────────┐

  │    which Java version compiles this                                 │
  │    which libraries are on the classpath                             │
  │    which plugins assemble the jar                                   │
  │                              │                                      │
  │                        mvn package                                  │
  │                              ▼                                      │
  │                          app.jar                                    │
  │                              ▲                                      │
  │            application.yml is packaged INSIDE this jar              │
  └─────────────────────────────────────────────────────────────────────┘
                                 │
  ② IMAGE BUILD — the Dockerfile copies the jar onto a JRE base image
                                 ▼
                   payflow/transactions:2026.09.21
                                 │
  ③ RUN TIME — on every environment, every restart, many times
  ┌─────────────────────────────────────────────────────────────────────┐
  │  compose.yml   (locally — an ECS task definition or a K8s            │
  │                 Deployment says the same things in production)      │

One question each

FileAnswers the questionActs atTo change it you must…
pom.xmlWhat capabilities does this application have at all?Build timerebuild, re-test, re-image, redeploy
application.ymlHow do those capabilities behave by default?Startup, from inside the jarrebuild — unless you left a ${VAR} hook

This is the sentence that matters in an incident. If the fix needs a new library, it needs a build, an image and a deploy — call it thirty minutes on a good day. If the fix is a value, it needs a restart — call it two minutes. Where a setting lives decides how fast you can recover from it. That is why mature services push as much as possible out of the jar and into the environment.

Which file wins when they disagree?

They do disagree, constantly — and that is by design. Spring Boot reads configuration from several places and applies a strict precedence order. Higher in this list beats lower. 

   WINS
    ▲   1. command-line arguments      java -jar app.jar --server.port=9000
    │   2. OS environment variables    SERVER_PORT=9000
    │                                     ◄── this is what compose.yml sets
    │   3. application-{profile}.yml   application-prod.yml
    │   4. application.yml             ◄── your defaults, baked into the jar
    │   5. library defaults            ◄── decided by what pom.xml put on the classpath
    ▼
   LOSES

figure 4 — the override chain; compose.yml wins over application.yml, always

Read that chain once more, because it contains the whole design. pom.xml supplies the floor — a library's own defaults. application.yml states what you want as a baseline. compose.yml — or an ECS task definition, or a Kubernetes ConfigMap — states what this environment wants, and it overrules everything below it.

The trick that makes this work in production

In PayFlow you wrote explicit hooks like ${ACCOUNTS_SERVICE_URL:http://localhost:8081}. Useful, but you do not actually need them. Any Spring property can be overridden by an environment variable, whether or not you planned for it, using a naming rule Spring calls relaxed binding: 

   upper-case everything · dots become underscores · hyphens disappear

   spring.datasource.url                     →  SPRING_DATASOURCE_URL
   server.port                               →  SERVER_PORT
   spring.jpa.open-in-view                   →  SPRING_JPA_OPENINVIEW
   spring.datasource.hikari.maximum-pool-size →  SPRING_DATASOURCE_HIKARI_MAXIMUMPOOLSIZE
   management.endpoints.web.exposure.include →  MANAGEMENT_ENDPOINTS_WEB_EXPOSURE_INCLUDE

figure 5 — the hyphen disappearing catches everyone once

That rule is why a platform team can operate your service without ever opening your source. They set variables in the task definition; your jar never changes. It is also the mechanical reason the twelve-factor rule "store config in the environment" is implementable at all.

So which file do I change?

   Does it need a NEW LIBRARY, or a Java / Maven change?      →  pom.xml
   Is it a BEHAVIOUR that is the same in every environment?   →  application.yml
   Does the VALUE DIFFER between dev, test and production?    →  compose.yml  (env var)
   Is it a SECRET?                                            →  a secret store, referenced
                                                                 by compose / task definition
   Is it the SHAPE of the database?                           →  a new Flyway .sql migration
   Is it about HOW THE IMAGE IS BUILT or WHO IT RUNS AS?      →  Dockerfile
   Is it CORRECTNESS — money, ordering, atomicity?            →  Java. No file will save you.

figure 6 — the decision rule; pin this one

Say this out loud

"pom.xml decides what the application can do, application.yml decides what it does by default, and the environment decides what it does here. Anything that varies by environment must be a variable, or you have three different artifacts pretending to be one."

PART FIVEWhat the container knew before it started

↑ contents

How did transactions know to look for accounts at that address? It didn't — not when the code was written. It was told at startup. 

   compose.yml                        application.yml
   ───────────                        ───────────────
   environment:                       accounts:
     ACCOUNTS_SERVICE_URL:              service:
       http://accounts:8081    ──────►    base-url: ${ACCOUNTS_SERVICE_URL:http://localhost:8081}
                                                      │                    │
                                        "use this variable"      "…or this, if it isn't set"

figure 7 — the same jar, three different addresses, zero rebuilds

Read ${NAME:fallback} as: "use the environment variable NAME; if it isn't set, use the value after the colon." Which gives you:

  • On your Mac, nothing set → falls back to localhost. Works as it always did.
  • In compose, the variable is set → uses accounts.
  • In AWS later, point it at a load balancer. Same jar. No rebuild.

This is the principle behind the phrase "build once, deploy anywhere": one artifact, configuration injected from outside. It is also why a database password should never sit in a file you commit — because then it isn't configuration, it's cargo.

PART SEVENThree settings worth understanding properly

↑ contents

ddl-auto — who is allowed to change the database structure?

DDL is Data Definition Language: the SQL that defines structure (CREATE TABLE, ALTER TABLE), as opposed to the SQL that moves data around. So ddl-auto asks: how much may Hibernate change the schema on its own?

ValueAt startup, Hibernate…Use it
nonedoesn't lookrarely
validatecompares every entity to the real tables and refuses to start on a mismatchevery environment
updatesilently creates and alters tables to match your Javanever
createdrops everything and rebuildsthrowaway test fixtures

Why update is dangerous: the schema stops being something you wrote down and reviewed, and becomes a side effect of whatever your Java classes happened to look like that day. Your migration files and your real database drift apart, and nobody notices until a fresh environment produces a schema no one recognises.

One system owns the schema. Here it's Flyway. Hibernate is only allowed to mark the homework.

open-in-view — how long do we hold a connection?

Your app borrows database connections from a small pool — ten by default. Every request takes one and gives it back. 

   request in
     │
     ├─ controller
     ├─ service        ◄── the actual database work happens here
     ├─ repository
     │
     ├─ Spring writes the JSON response
     │
   response out

   open-in-view: TRUE    ├──────────────────────────────────┤   held all the way
   open-in-view: FALSE   ├─────────────┤                        released early

figure 9 — the same request, two very different connection lifetimes

true is Spring Boot's default. It exists so that lazily-loaded relationships still work if the JSON writer touches one. The cost is real: with ten connections, ten slow clients and everything queues behind them — while no database work is happening at all.

Actuator — the health endpoint you didn't write

Add spring-boot-starter-actuator and you get /actuator/health for free. It isn't just "the process is alive" — Spring checks that the database answers and Flyway ran, so UP means genuinely ready to serve traffic.

That's why compose can say "don't start transactions until accounts is healthy". It's also the same mechanism Kubernetes uses for liveness and readiness probes, which is the next place you'll meet it.

Performance and capacity

SCENARIO 1

"It is fine at 50 transfers a second. At 400 it collapses with connection timeouts."

What is actually happening. Every request that touches the database borrows one connection from a pool of ten and gives it back. Little's Law tells you how many you need: concurrency = throughput × latency. At 400 requests per second with a 25 ms database call, that is 400 × 0.025 = 10 connections just to break even, with zero headroom. The moment Postgres slows to 40 ms you need sixteen, the queue for a connection grows faster than it drains, and requests start failing. The timeouts you see are not database timeouts. They are waiting-for-a-connection timeouts, which is a completely different diagnosis.

application.ymlcompose.yml
# application.yml — the behaviour, and a safe default
spring:
  datasource:
    hikari:
      maximum-pool-size: ${DB_POOL_MAX:10}
      minimum-idle: ${DB_POOL_MIN:10}      # same as max — avoid pool churn under spiky load
      connection-timeout: 2000             # ms to wait for a free connection, then fail fast
      max-lifetime: 1200000                # 20 min — retire before the DB or a proxy does it for you
      validation-timeout: 1000
      leak-detection-threshold: 20000      # log a stack trace if code holds one for 20s
# compose.yml — the value THIS environment wants
services:
  transactions:
    environment:
      DB_POOL_MAX: 20

The arithmetic nobody does until it breaks. instances × maximum-pool-size ≤ postgres max_connections − reserved. Six instances at twenty connections each is 120. PostgreSQL ships with max_connections = 100. You will run out of database long before you run out of application, and the failure will look like your application's fault. If you need more, a connection proxy such as PgBouncer or RDS Proxy sits in between and multiplexes — that is a topology change, not a config change.

The architect's line. "The pool is a queue, not a cache. I size it from Little's Law, then check it against the database's connection ceiling across all instances — because the pool is the first place a latency problem turns into an outage."

What it costs. A bigger pool does not make the database faster. Past the point where Postgres is CPU-bound, more connections means more context switching and worse latency for everyone. A short connection-timeout with a fast failure is almost always better than an unbounded wait, because a failure you can see beats a hang you cannot.

SCENARIO 2

"The container keeps dying under load with exit code 137."

What is actually happening. 137 is 128 + 9 — the process was SIGKILLed, and under load that means the kernel's out-of-memory killer. The JVM sized its heap from what it believed was available, the container's cgroup limit was lower, and the JVM's total footprint went past it. Heap is not the process. The process is heap plus metaspace plus thread stacks plus the code cache plus direct byte buffers plus GC structures.

compose.yml

Note where this is not: application.yml. The JVM has already sized its heap before Spring exists, so heap settings must arrive as JVM flags, which means the environment.

services:
  transactions:
    environment:
      JAVA_TOOL_OPTIONS: >-
        -XX:MaxRAMPercentage=70
        -XX:+ExitOnOutOfMemoryError
        -XX:+HeapDumpOnOutOfMemoryError
        -XX:HeapDumpPath=/tmp
    deploy:
      resources:
        limits:       { cpus: '2.0', memory: 1G }
        reservations: { cpus: '0.5', memory: 512M }

The rule of thumb: heap gets 70–75% of the container limit; the remaining quarter is everything else the JVM needs. MaxRAMPercentage is the right flag rather than a fixed -Xmx, because it follows the container limit when you resize the task.

The CPU half of this, which is missed more often. The JVM sizes its GC threads, the common ForkJoinPool and several library thread pools from availableProcessors(). A CPU limit of 0.5 reports one processor, so parallel streams silently become serial and your throughput model is wrong. CPU limits change application behaviour, not just speed.

The architect's line. "Container memory limit and JVM heap are two different numbers, and the heap must be the smaller of the two. Exit 137 is the kernel telling you it made that decision on your behalf."

What it costs. ExitOnOutOfMemoryError means the instance dies instead of limping — which is what you want, because a JVM in GC thrash serves every request slowly and stays "healthy" to a naive health check. You are trading a fast, visible restart for a slow, invisible degradation. Take the trade.

SCENARIO 3

"The service is unresponsive, but CPU is at 3% and the database is idle."

What is actually happening. Thread pool exhaustion. Every in-flight HTTP request holds one of Tomcat's 200 threads for its entire duration — including the time it spends waiting on a downstream call that is never going to answer. Two hundred threads multiplied by one hung dependency and the service is gone while doing no work at all. This is the signature failure of a synchronous architecture, and the give-away is exactly what you are seeing: an outage with an idle CPU.

application.yml
server:
  tomcat:
    threads:
      max: 200
      min-spare: 20
    accept-count: 100          # OS-level queue; beyond this, connections are REFUSED
    max-connections: 8192
    connection-timeout: 5s
spring:
  jpa:
    open-in-view: false        # give the connection back before the JSON is written

Why refusing connections is the good outcome. When the accept queue is full the operating system rejects new connections immediately. That is load shedding: the caller finds out now, retries elsewhere, and the queue does not grow invisibly. The alternative — a deep queue — means every request waits, every client times out anyway, and you have burned resources producing responses nobody is still listening for. Bounded queues with fast rejection beat unbounded queues, always.

The architect's line. "Thread pool exhaustion presents as a CPU-idle outage. The fix is a timeout on the dependency, not more threads — more threads just buys you a larger failure."

What it costs. Raising threads.max feels like the fix and is almost never the fix: each thread is a stack allocation, and each one that gets through holds a database connection you do not have. See scenario 5 for the actual remedy.

SCENARIO 4

"Month-end reporting queries are slowing down live payments."

What is actually happening. One database is serving two workloads with completely different shapes — short, latency-critical transactional writes, and long analytical scans that evict the buffer cache the payment path depends on. They are competing for the same CPU, the same memory and the same connections.

application.ymlcompose.yml
# application.yml
app:
  datasource:
    primary:
      url: ${DB_PRIMARY_URL}
      hikari: { maximum-pool-size: 20 }
    replica:
      url: ${DB_REPLICA_URL:${DB_PRIMARY_URL}}   # falls back to primary locally
      hikari: { maximum-pool-size: 10, read-only: true }

In code, a routing DataSource sends anything inside @Transactional(readOnly = true) to the replica.

The trade-off you must name out loud. Replication is asynchronous. A balance read taken immediately after a transfer may return the old number, because the replica is a few hundred milliseconds behind. So the rule is: all writes, and any read-after-write the customer will notice, go to the primary. Only genuinely lag-tolerant reads — statements, reconciliation, reporting, fraud model training — go to the replica. If you cannot say which of your reads are lag-tolerant, you are not ready to add a replica.

The architect's line. "Splitting reads is a consistency decision before it is a performance decision. I would move reporting to a replica and measure replication lag as an SLI, with an alert, because lag is now part of my correctness story."

Resilience

SCENARIO 5

"accounts is down, and transactions hangs instead of failing."

What is actually happening. The outbound call has no timeout. A socket that connects and then goes quiet will wait a very long time, and every waiting request is holding a Tomcat thread — which is scenario 3, arriving from a different direction. A missing timeout is how one dependency's outage becomes everyone's outage.

pom.xmlapplication.yml
<!-- pom.xml — this is a new capability, so it needs a build -->
<dependency>
  <groupId>org.springframework.cloud</groupId>
  <artifactId>spring-cloud-starter-circuitbreaker-resilience4j</artifactId>
</dependency>
# application.yml
accounts:
  service:
    base-url: ${ACCOUNTS_SERVICE_URL:http://localhost:8081}
    connect-timeout: 500ms      # TCP handshake — if this is slow, the host is gone
    read-timeout: 2s            # waiting for the response body

resilience4j:
  circuitbreaker:
    instances:
      accounts:
        sliding-window-type: COUNT_BASED
        sliding-window-size: 50
        failure-rate-threshold: 50           # >50% failures in the last 50 calls → open
        wait-duration-in-open-state: 10s     # stop calling entirely for 10s
        permitted-number-of-calls-in-half-open-state: 5
  retry:
    instances:
      accounts:
        max-attempts: 3
        wait-duration: 200ms
        exponential-backoff-multiplier: 2
        retry-exceptions:
          - java.io.IOException

The latency budget nobody checks. Three attempts at a 2-second read timeout is a six-second worst case. If your API promises a 1-second P99, that configuration is a promise you cannot keep. Your own SLA must be larger than the sum of your downstream timeouts multiplied by your retries, or the retry policy is quietly the thing breaking your SLA.

Two rules that carry the most weight. First, the circuit breaker sits outside the retry — otherwise retries pile load onto a dependency that is already failing and you have built a denial-of-service against yourself. Second, only retry idempotent operations. Retrying a debit without an idempotency key debits twice, and in payments that is not an incident, it is a remediation programme.

The architect's line. "Every remote call gets a connect timeout, a read timeout, a bounded retry with jittered backoff, and a circuit breaker outside the retry. And I only retry operations that are safe to repeat — which usually means an idempotency key on the request."

What it costs. A circuit breaker fails fast when the dependency is recovering too, so you need a sensible half-open probe. And you now have to answer a product question: when the circuit is open, what does the customer see? Queue it, degrade it, or refuse it — that is a business decision, and it belongs in the design, not in the YAML.

SCENARIO 6

"Every deploy shows up as a spike of 502s."

What is actually happening. The orchestrator sends SIGTERM, the process exits, and every request that was mid-flight dies with it. Graceful shutdown means: stop accepting new work, let in-flight work finish, then exit.

application.ymlcompose.yml
# application.yml
server:
  shutdown: graceful                    # Spring Boot 4 default; Boot 3 defaulted to immediate
spring:
  lifecycle:
    timeout-per-shutdown-phase: 25s     # how long the app will wait for in-flight work
# compose.yml
services:
  transactions:
    stop_grace_period: 40s              # how long Docker waits before SIGKILL

The ordering rule, and it is the whole point of this scenario. stop_grace_period must be longer than timeout-per-shutdown-phase. Get it backwards and Docker SIGKILLs the process halfway through draining — which is precisely the failure graceful shutdown was added to prevent, now with extra configuration. The same rule applies in ECS (stopTimeout) and Kubernetes (terminationGracePeriodSeconds).

The half that configuration cannot do. The load balancer must stop sending new requests before the app starts draining. In Kubernetes that is a preStop sleep; on an ALB it is the deregistration delay. Without it you drain gracefully while the balancer cheerfully keeps handing you new work.

The architect's line. "Draining is a three-party agreement between the load balancer, the orchestrator and the application, and their timeouts have to be ordered: deregistration first, then the app's drain window, then the orchestrator's kill."

SCENARIO 7

"A new instance receives traffic a second before it can serve it."

What is actually happening. The health check is answering "the process started" rather than "this instance can do useful work". Those are two different questions and they need two different endpoints.

application.ymlcompose.yml
# application.yml
management:
  endpoint:
    health:
      probes:
        enabled: true
      show-details: when-authorized
      group:
        liveness:
          include: livenessState          # am I wedged? if so, restart me
        readiness:
          include: readinessState, db     # can I serve right now? if not, route around me
# compose.yml
    healthcheck:
      test: ["CMD","curl","-f","http://localhost:8081/actuator/health/readiness"]
      interval: 10s
      timeout: 3s
      retries: 3
      start_period: 45s        # JVM startup is not a failure

Put the database in readiness, never in liveness. If a database check is part of liveness, a thirty-second database blip restarts every instance simultaneously, they all come back cold, they all hammer the recovering database, and you have converted a blip into an outage. This is one of the most common self-inflicted incidents in container platforms.

The architect's line. "Liveness answers 'restart me', readiness answers 'route to me'. A shared dependency belongs in readiness only, because liveness on a shared dependency turns a partial failure into a correlated one."

Observability

SCENARIO 8

"The payment took nine seconds. Nobody can say which hop was slow."

What is actually happening. You have logs per service and no way to stitch them into one request. Distributed tracing gives every request an id at the edge and propagates it across every boundary, so nine seconds becomes "seven of them were in the accounts call, and six of those were waiting for a connection."

pom.xmlapplication.ymlcompose.yml
<!-- pom.xml -->
<dependency>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-starter-opentelemetry</artifactId>
</dependency>
# application.yml
management:
  tracing:
    sampling:
      probability: ${TRACE_SAMPLE:0.1}       # Boot's own default is 0.1
  opentelemetry:
    tracing:
      export:
        otlp:
          endpoint: ${OTLP_ENDPOINT:http://otel-collector:4318/v1/traces}
# compose.yml
  otel-collector:
    image: otel/opentelemetry-collector-contrib:latest
    ports: ["4318:4318"]
# and on each service:
    environment:
      TRACE_SAMPLE: "1.0"                    # 100% locally; 1–10% in production

The sampling trade-off. Head-based sampling decides at the start of the request, so it is cheap, but it throws away traces before it knows whether they were interesting — and the interesting ones are the slow and failing ones. Tail-based sampling buffers the whole trace in a collector and decides at the end, so it can keep every error and every trace over your latency threshold plus a small random sample of the healthy ones. It costs you a collector with memory and state. In a payments system that cost is usually worth it.

The architect's line. "Trace context has to cross every boundary — the HTTP header, the Kafka record header, the SQS message attribute. If it does not, the trace stops at the queue, and the queue is precisely where the latency was."

SCENARIO 9

"We found out from the customer, not from a dashboard."

pom.xmlapplication.ymlcompose.yml
<!-- pom.xml -->
<dependency>
  <groupId>io.micrometer</groupId>
  <artifactId>micrometer-registry-prometheus</artifactId>
</dependency>
# application.yml
spring:
  application:
    name: transactions
management:
  endpoints:
    web:
      exposure:
        include: health,info,prometheus     # never "*" in production — see scenario 11
  metrics:
    tags:
      application: ${spring.application.name}
      environment: ${ENVIRONMENT:local}

Cardinality is the trap. Never tag a metric with an account id, a transaction id, a customer id or a raw URL path. Every distinct tag value creates a new time series. One tag with a million values will take down your metrics backend — not your application, your monitoring, in the middle of the incident it was meant to explain. Identifiers belong in traces and logs, never in metric labels.

What to actually measure. The four golden signals — latency, traffic, errors, saturation — and then at least one business metric such as a payflow.transfers.completed counter. "The JVM is healthy" does not tell you that money stopped moving; a flat transfer counter does, and it does it before the customer calls.

The architect's line. "I alert on symptoms customers feel — error rate and latency against the SLO — and I keep resource metrics for diagnosis rather than paging. Paging on CPU produces alert fatigue and misses the outages that matter."

SCENARIO 10

"The logs are there. Searching them is hopeless."

What is actually happening. Human-readable log lines are unparseable at scale. Structured logging emits one JSON object per event, so every field is queryable and — once tracing is on — every line carries the trace id, which is what lets you pivot from a log to the full request.

application.ymlcompose.yml
# application.yml
logging:
  structured:
    format:
      console: ecs             # also: gelf, logstash
  level:
    root: INFO
    com.payflow: ${LOG_LEVEL:INFO}
# compose.yml — rotation is an environment concern, not an application one
    logging:
      driver: json-file
      options:
        max-size: "10m"
        max-file: "3"

Two things that bite in production. Without rotation, one chatty service fills the host disk — and a full disk takes down every container on that host, not just the noisy one. And never log a PAN, a CVV, a full account number, an access token or a customer's personal data: mask at the boundary where the value enters, not in the log appender, because the appender is the last place anyone remembers to change.

The architect's line. "Logs, metrics and traces answer different questions — what happened to this one request, what is happening in aggregate, and where did the time go. I correlate them with a trace id in the MDC, and I keep identifiers out of metric labels."

SCENARIO 11

"A scan found /actuator/env reachable from the internet."

What is actually happening. Somebody set include: "*" to make debugging easier. That exposes /actuator/env — your entire resolved configuration — and /actuator/heapdump, which is the contents of your process memory, including credentials and live customer data. This is a data breach with a YAML root cause.

application.ymlcompose.yml
# application.yml — move management to its own port
management:
  server:
    port: 9090
  endpoints:
    web:
      exposure:
        include: health,info,prometheus
  endpoint:
    health:
      show-details: when-authorized
# compose.yml — publish the business port only
    ports:
      - "18082:8082"          # 9090 is deliberately NOT published:
                              # reachable inside the network, nowhere else

Moving management to a second port turns "who is allowed to see this" from an application concern into a network concern — a security group, a listener rule, a network policy. That is a much stronger control than an authentication filter, because it fails closed and it does not depend on anyone remembering to configure it correctly next time.

The architect's line. "Operational endpoints get their own port and their own network path, and only the endpoints we actually consume are exposed. Defaults that are convenient in development are an attack surface in production."

Secrets and hardening

SCENARIO 12

"The database password is in compose.yml, and compose.yml is in git."

What is actually happening. Configuration and secrets have been treated as the same thing. They are not: configuration is reviewed in a pull request and lives forever in history, and a secret must never appear in one. Once a credential is committed it is compromised — deleting the line does not remove it from the history, and rotating it is now the only remedy.

compose.yml
# compose.yml — local development
secrets:
  db_password:
    file: ./secrets/db_password.txt     # and ./secrets/ is in .gitignore

services:
  transactions:
    secrets: [db_password]
    environment:
      SPRING_DATASOURCE_PASSWORD_FILE: /run/secrets/db_password

In production the value never exists in a file you author at all. An ECS task definition references a Secrets Manager ARN and the agent injects it at task start; the thing your service is — its IAM task role — is the identity, and the password is just a consequence of it.

The better answer is to have no password. RDS IAM authentication lets the task exchange its IAM role for a token that is valid for fifteen minutes. There is no long-lived credential to rotate, to leak, or to find in a log. If someone asks you how you would handle credential rotation, the strongest answer is that you would remove the credential.

The architect's line. "Configuration and secrets have different lifecycles and different blast radii. I keep secrets out of the artifact and out of the repository, inject them at start-up from a managed store, and prefer short-lived identity-based credentials over any secret that needs rotating."

SCENARIO 13

"The image is 900 MB, runs as root, and every deploy pushes the whole thing."

pom.xmlDockerfilecompose.yml
<!-- pom.xml — layered jars, so Docker can cache the slow-changing parts -->
<plugin>
  <groupId>org.springframework.boot</groupId>
  <artifactId>spring-boot-maven-plugin</artifactId>
  <configuration>
    <layers><enabled>true</enabled></layers>
  </configuration>
</plugin>
# compose.yml — runtime hardening
    read_only: true
    tmpfs: [/tmp]
    cap_drop: [ALL]
    security_opt: ["no-new-privileges:true"]
    user: "1000:1000"

Why layered jars are an architecture point rather than a build trick. Your dependencies are roughly 60 MB and change monthly; your own classes are roughly 2 MB and change hourly. If they are in the same image layer, every single deploy pushes and pulls 60 MB it did not need to. Split them and a code-only deploy moves 2 MB. Multiply by deploys per day, services, and environments, and it becomes deploy latency, registry cost and rollback speed — every day, forever.

The architect's line. "Smallest possible base image, non-root user, read-only root filesystem, no added capabilities, and layers ordered by rate of change. Image size is both an attack surface and a deploy-time cost."

Data and correctness

SCENARIO 14

"We need a new column on transactions, with no downtime."

V7__add_reference.sqlapplication.yml (unchanged)

The thing to understand first: during a rolling deploy, the old code and the new code are running at the same time, against the same database. Every schema change therefore has to be compatible with both. That constraint is the whole reason for the three-step dance.

-- STEP 1 — EXPAND.  Deployable while the old code is still running.
ALTER TABLE transactions ADD COLUMN reference VARCHAR(64);   -- nullable, no default rewrite
-- deploy code that WRITES both old and new, READS old

-- STEP 2 — MIGRATE.  Backfill in batches so you do not lock the table.
UPDATE transactions SET reference = ... WHERE reference IS NULL AND id BETWEEN ? AND ?;
-- deploy code that READS new

-- STEP 3 — CONTRACT.  Only once nothing reads the old shape.
ALTER TABLE transactions ALTER COLUMN reference SET NOT NULL;
ALTER TABLE transactions DROP COLUMN old_column;

ddl-auto stays on validate throughout. That is the guard that catches a forgotten migration at startup in the pipeline, rather than as a column does not exist error at two in the morning.

Never edit a migration that has already run. Flyway stores a checksum of every applied file and will refuse to start if one changes — which is the feature working, not a bug. You correct a mistake by adding a new migration, always.

The architect's line. "Schema changes are expand, migrate, contract, because during a rolling deploy two versions of the code share one database. Migrations own the schema and the ORM only validates it."

SCENARIO 15

"A transfer debited Alice and never credited Bob."

This one is here to mark a boundary. No setting in any of the three files fixes it. The debit and the credit are two HTTP calls against two databases with nothing making them atomic, and a crash between them leaves money missing. That is a design problem.

V8__outbox.sqlpom.xmlJava

The shape of the answer is the transactional outbox: write the ledger row and an outbox row in the same local database transaction, so either both exist or neither does, and have a separate relay publish the outbox row afterwards. The transfer becomes a saga with an explicit compensating entry rather than a distributed transaction, and the consumer must be idempotent because the relay will occasionally deliver twice.

The architect's line. "Configuration tunes a system; it cannot make it correct. Atomicity across two services is a design decision — an outbox with an idempotent consumer, or a saga with an explicit compensation — and I would not try to solve it with a transaction manager."

Build and cost

SCENARIO 16

"Every commit downloads the whole internet. CI takes nine minutes."

Dockerfilepom.xml
FROM maven:3.9-eclipse-temurin-25 AS build
WORKDIR /build
COPY pom.xml .                                  # ① changes rarely
RUN mvn -B -q dependency:go-offline             # ② this layer is now cached
COPY src/ src/                                  # ③ changes constantly
RUN mvn -B -q clean package -DskipTests

The rule. Docker caches each instruction as a layer and invalidates every layer after the first one that changed. Copy slow-changing files before fast-changing ones and a code-only commit reuses the dependency layer instead of re-resolving it. Reverse those two COPY lines and every one-character change re-downloads everything.

And pin your versions. :latest means the image you tested is not necessarily the image you shipped, which breaks reproducibility and is a live supply-chain risk. Pin the base image by tag or digest, and pin dependency versions through a BOM in <dependencyManagement> rather than scattering them.

The architect's line. "Build layers are ordered by rate of change, and every input is pinned. A build that is not reproducible is not auditable, and in a regulated environment that is the part that fails the review."

PART ELEVENThe whole thing in six sentences

↑ contents

  1. A container is a standard box holding an application and everything it needs, so the host doesn't have to care what's inside.
  2. An image is the frozen template; a container is a running instance of it — class and object.
  3. Inside a container, localhost means that container, so services address each other by service name and published ports exist only for outside traffic.
  4. Configuration arrives from the environment at startup, so one image promotes unchanged from laptop to production.
  5. Migrations own the database schema and the ORM only validates it, because a schema that changes as a side effect is a schema nobody controls.
  6. Connections are a small shared pool, so anything that holds one longer than it needs is a limit on how many people you can serve.
  7. pom.xml decides what the application can do, application.yml decides what it does by default, and the environment decides what it does here — and that ordering is also the ordering of how long each fix takes.
