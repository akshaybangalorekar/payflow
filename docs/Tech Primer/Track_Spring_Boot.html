Unit 1 · The container & dependency injection

@SpringBootApplication scans your packages for stereotype annotations (@RestController, @Service, @Repository), instantiates each class as a bean — one singleton instance — and injects them into each other's constructors. You never write new for a dependency again; the container builds the object graph at startup.

// from YOUR code — the controller never constructs its service:
public AccountController(AccountService accountService) {
    this.accountService = accountService;   // injected by the container
}

Unit 2 · The request lifecycle

Every request walks the same corridor. You captured this in your debugger stack trace:

HTTP request
 → Filter chain            (logging; later: security — Stage S)
 → DispatcherServlet        (the traffic cop)
 → handler mapping          (finds your @PostMapping("/api/accounts"))
 → Jackson parses JSON      (string → CreateAccountRequest object)
 → @Valid runs              (rejects bad input BEFORE your method)
 → your controller method   (called via reflection)
 → return value → JSON   (Jackson again)
 → 201 response
 anything thrown anywhere → @RestControllerAdvice
Unit 3 · Spring Data JPA & Hibernate

You wrote an interface with no implementation — Spring generates one at runtime. Derived queries: the method name is the query.

boolean existsByEmail(String email);
// becomes: SELECT 1 FROM accounts WHERE email = ? LIMIT 1

accountRepository.save(account);   // INSERT (or UPDATE if it has an id)

Coming attractions: lazy loading and the N+1 query problem (one query for the list, then one more per item — the classic production killer we will hunt with logs).

Unit 4 · Validation & binding

The DTO is the contract; annotations declare its rules; @Valid enforces them at the door:

// on the DTO (the contract):
@NotBlank String customerName,  @Email String email

// on the controller (enforcement):
public ResponseEntity create(@Valid @RequestBody CreateAccountRequest req)

// on failure: MethodArgumentNotValidException → your handler → clean 400 JSON
Unit 5 · Configuration & profiles

application.yml is layered: defaults → profile file (application-dev.yml) → environment variables (SPRING_DATASOURCE_PASSWORD) → command line. The environment always wins — that's how the same jar runs on your Mac and in AWS with different databases, no code change:

spring:
  config:
    activate:
      on-profile: dev     # only loads when profile "dev" is active
  datasource:
    url: jdbc:postgresql://localhost:5432/payflow_accounts
Unit 6 · Transactions

@Transactional on a service method = everything inside is one ACID unit: all writes commit together or none do. This is where your race gets fixed for real — the database itself becomes the referee:

@Transactional
public Account create(CreateAccountRequest req) { ... }
// method exits normally → COMMIT. Exception → ROLLBACK.
Unit 7 · Testing

Three depths: unit tests (JUnit + Mockito, milliseconds, mock the dependencies you learned to inject in Unit 1), slice tests (@WebMvcTest boots only the web layer), and integration tests (Testcontainers starts a real Postgres in Docker for the test, throws it away after):

@Test
void rejectsDuplicateEmail() {
    when(repo.existsByEmail("a@b.c")).thenReturn(true);
    assertThatThrownBy(() -> service.create(req))
        .isInstanceOf(DuplicateAccountException.class);
}
Unit 8 · The rest, on schedule

Security filter chain (Stage S — OAuth2 lands between the filters of Unit 2's corridor), Kafka listeners (Stage 2 — a method invoked by a message instead of a request), Micrometer metrics (Stage 3). Each gets its concept block when the stage arrives — taught in context, not in the abstract.
