PayFlow Track · The Spring Universe

One payment's journey through Spring

Every Spring project that matters, told as the story of one ₹5,000 payment — because you already live in this story: it's PayFlow.

Why "Spring" feels like a maze

Spring is not one thing. It's a small core (the Spring Framework: the IoC container you already know) plus dozens of satellite projects built on that core, each solving one production problem. The confusion evaporates once you see them as departments of one building — so here's the tour. Priya taps "Pay" in her banking app at 7:04 PM, sending ₹5,000 to a merchant. Watch who does what.

THE FOUNDATION — BEFORE 7:04 PM Spring Framework (core)

The ground the building stands on

None of the tour happens without this: the IoC container that scans, builds, and wires beans, injecting dependencies through constructors. You learned it in Unit 1 with your own AccountController. Every satellite project below is "just beans": Spring Security is a chain of filter beans, Spring Data manufactures repository beans, Kafka support is listener beans. Learn the container once and every Spring project becomes vocabulary, not mystery.

THE CAST — WHO WORKS IN THIS BUILDING basic building blocks

Before the story: meet the staff

The bean is the permanent staff. Hired once at startup, one per role (a singleton), employed for the life of the app: AccountService, AccountController, the repository proxy — each is exactly one object serving every request on every thread. Careful what you leave on their desks: shared staff means no per-request state on beans — your race-condition lesson, restated as office policy.

The object is the paperwork. Priya's payment, the parsed request, the response being assembled — created per request, thousands a minute, short-lived, unmanaged by the container. Staff (beans) process paperwork (objects); paperwork never becomes staff — you'd never mark a DTO with @Component, because one shared request-object for the whole app would be nonsense.

The stereotype annotation is the job ad that gets you hired: @Component (general staff), @Service (business rules), @Repository (data access), @RestController (front desk). To the container they're identical — a badge saying "employ me at startup" — the specific badge documents the job for human readers.

Dependency injection is day-one orientation: the container hands each new hire their colleagues by calling their constructor. Nobody recruits their own team — you never write new AccountService(...); you declare "I need one" and the container supplies it. That's what makes testing possible: hand the same constructor a mock instead of a real colleague.

The proxy is the body double: for staff with special duties, the container hires a stand-in that wraps the real one. You talk to the double; it does the extra chore around each call (opens and closes a transaction, checks a cache), then relays to the real employee. The repository proxy you met in Unit 3 is exactly this; @Transactional will work the same way.

Configuration (application.yml) is the notice board in reception: port, database location, feature switches. Same staff, different boards per environment — that's what profiles change — and environment variables pin extra notices on top, which is how one jar runs on your Mac and in AWS unchanged.

Every department in the tour below is staffed by exactly these players. Watch for them as you read.

The cast, at rush hour — one picture

How to read this picture: it's rush hour in one department. The three horizontal lanes are threads — Tomcat hands every incoming request its own courier thread. The tall boxes are beans — permanent staff, exactly one of each, hired at startup; every courier passes through the same boxes. The yellow notes are objects — paperwork born fresh for each request, carried by its own courier, discarded afterwards. The dashed box around the repository is the proxy, the body double. And the dashed green arrow along the bottom is Thread-1's return trip: the same courier (green = Thread-1) walking back out with different paperwork — the AccountResponse the controller built. Solid arrow in with the request, dashed arrow out with the response; one thread, one round trip. It's routed along the bottom only for readability — physically the response passes back through the controller on its way to the door. The numbered circles match the three cards below the picture.

1 · The proxy — why a body double?

Your code calls existsByEmail() — but you're not talking to a real repository. You're talking to a stand-in the container built around the real one (SimpleJpaRepository, inside the dashed box). Why bother? Because the stand-in can do extra chores around every single call without the real employee — or your code — knowing: open a transaction before, commit/roll it back after (that's how @Transactional will work), check a cache, add timing metrics. You call a method; the double intercepts, does its chores, relays the work inside. You never notice the swap — that's the entire point.

2 · Threads — one desk, many couriers

Tomcat hands each incoming request its own thread — think of the thread as the courier who walks one piece of paperwork through the department. The picture's key fact: all couriers pass through the SAME staff. One AccountService box, three simultaneous couriers. Now imagine the service desk had a drawer (a mutable field) where a courier could leave papers: courier B opens the drawer and finds courier A's papers. That is exactly the race you proved with two rows — two threads interleaving inside one shared bean. Staff rule: the desk stays empty; all state rides in the paperwork the courier carries.

3 · Why a DTO is never staff

Mark CreateAccountRequest with @Component and the container does what it always does with staff: hires ONE, at startup, shared by all threads, forever. Now Priya, Rahul and Sneha all scribble on the same single form — your email ends up in my payment, the race again but worse. Paperwork must be born fresh per request (Jackson births it each time it parses a request body), do its job, and be discarded. Staff = few and permanent; paperwork = many and disposable. The two lists never mix.

7:00 PM — THE BUILDING ITSELF Spring Boot

The pre-wired building

Spring Framework alone is raw plumbing; Boot is the building with electricity, doors, and staff pre-installed. Three superpowers: starters (one dependency pulls in a whole coherent stack — spring-boot-starter-webmvc brought Spring MVC + Jackson + Tomcat into your jar), auto-configuration (it saw JPA + Postgres on your classpath and built the datasource without you asking), and the embedded server. About that embedded server — it's not a rival of Tomcat; Tomcat IS the embedded server. Old-world Spring apps were packaged as .war files that you dropped into a separately installed Tomcat living on a server somewhere; Boot flipped the relationship — Tomcat ships as a library that starts inside your own JVM. That's why java -jar app.jar just… serves HTTP: your app is not deployed to a server, it is the server. (Alternatives exist — Jetty, Undertow — swappable by swapping the starter; teams rarely bother.) Profiles (application-dev.yml vs prod) mean the same jar behaves differently per environment.

7:04:00 — RECEPTION Spring MVC

The request walks in

Priya's payment hits POST /api/transactions. Spring MVC's use: it's the translation layer between HTTP and Java. URL routes map to controller methods (@PostMapping), path variables become method arguments (@PathVariable), and whatever your method returns becomes the HTTP response. Without it, you'd be hand-parsing raw HTTP requests for a living. The DispatcherServlet (the traffic cop) routes each request to the right method — your unit-2 corridor: filter → dispatcher → Jackson parses JSON → @Valid → controller method → response serialized.

And Jackson? A separate JSON library, not part of Spring — Spring MVC just hires it as the translator on both ends of the desk. HTTP carries text; Java speaks objects. Incoming: Jackson turns the JSON string of Priya's payment into a CreateTransactionRequest object before your method ever runs. Outgoing: it turns your returned object back into JSON text after your method returns. When you watched internalNotes vanish from your API responses, that was Jackson faithfully serializing every getter of whatever object the controller returned — which is exactly why flaw 2 was fixed by handing it a smaller object, not by teaching Jackson to hide things. This whole department is the one you know best: it's your accounts service, and the transactions service you're about to build.

7:04:01 — THE GUARD Spring Security

ID check, before the front desk

Before any controller runs, the request passes a chain of security filters: who are you (JWT token / OAuth2 login), what may you do (roles)? This is why your accounts API is currently "open to anyone" — no security filter chain exists yet. When we bolt one on (Stage S), the guard stands in front of reception, rejecting forged requests before your code ever sees them. In your Q2 language: the controller sees only authenticated calls, the way the customer view DTO sees only allowed fields — enforced by a layer, not by hope.

7:04:02 — THE LEDGER CLERK Spring Data JPA

Money in, money written, exactly once

The transaction service loads Priya's account and the merchant's account (proxies, derived queries — Unit 3), debits one, credits the other, saves. The clerk's iron rule is @Transactional: both legs commit together or neither does — money never evaporates mid-journal-entry. That's where you're headed next: optimistic locking on balances so two simultaneous payments can't both read "balance: 5000" and both spend it. Your race-condition scar, at money scale.

7:04:03 — THE MESSENGER Spring for Kafka

Departments that don't wait for each other

The moment the ledger entry commits, the transactions service publishes txn.created to Kafka — a note on a conveyor belt — and immediately returns "processing" to Priya. Downstream, asynchronously: notifications sends the SMS, analytics updates dashboards, the fraud service scores it. Nobody blocks anybody. In Stage 2 you'll write both ends: @KafkaListener methods — beans invoked by a message instead of a request. The contract between departments is a schema (Avro) in a schema registry, not a Java interface.

7:04:04 — FRAUD DEPT IS AT LUNCH Spring Cloud + Resilience4j

Don't wait for a dead department

What if the fraud service is down? Without protection, every payment hangs on it. The circuit-breaker pattern (Resilience4j, wired in through Spring Cloud): call with a timeout, on repeated failure open the circuit and use a fallback (queue for manual review) instead of queueing doomed calls — then probe to close it again. Spring Cloud's wider job is the multi-office building: an API Gateway as the single public door, service discovery (the building directory: "where does 'fraud' live this second?"), and a config server so thirty services read one source of truth. PayFlow grows into this in Stage 3.

7:04:05 — RECEIPT (you built this already)

"202 Accepted, payment processing"

Priya gets her receipt in 300 milliseconds because the heavy lifting went to the conveyor belt. That 202-vs-201 distinction — accepted vs completed — is the difference between a synchronous world and an event-driven one, and it's the biggest architectural step in our whole project.

11:00 PM — NIGHT SHIFT Spring Batch

The accountant who works while you sleep

End of day: millions of transactions to reconcile, statements to generate, interest to post. Spring Batch runs chunked, restartable jobs — read 1,000 records, process, write, checkpoint, repeat; die at 2 AM, resume from the checkpoint, never reprocess. It's the classic banking workhorse, and where PayFlow's statement endpoints will eventually get their data from.

NEXT MORNING — "WHERE'S MY MONEY?" Spring AI

The support agent who read every manual

Priya asks the in-app assistant. Spring AI standardizes talking to LLMs the way Spring Data standardizes databases: one API, many providers — OpenAI-compatible hosted APIs or a local model via Ollama on your Mac (our Stage 4: zero cost, full control). The killer pattern is RAG: retrieve her actual transaction, stuff it into the prompt as context, and let the model answer about her payment, not payments in general. The chatbot bean is just another bean.

THE WHOLE TIME — CCTV Actuator + Micrometer

The building's nervous system

Every department reports its vitals: Spring Actuator exposes /actuator/health, /actuator/metrics; Micrometer pipes numbers to Prometheus; Grafana draws the dashboards ops stares at. "Payments per second," "p99 latency," "circuit open?" When something breaks at scale, this is how you find out before customers tell you — Stage 3. You've already met the baby version: the actuator prompt you declined in week one.

The performance wing — when 10,000 payments/second arrive

Three rungs on the performance ladder, in the order real teams climb them. One: measure first (Micrometer + load tests — most "slow" services are one bad N+1 query, which you now know how to hunt). Two: cache (Spring Cache: @Cacheable on that expensive call) and pool connections properly. Three: change the threading model — and here Java itself split into two philosophies. Virtual threads (Java 21+): ordinary blocking code, but each request gets a thread so cheap you can have a million — the modern default, and PayFlow's payout batch will use them. Spring WebFlux (reactive): a fully non-blocking pipeline where nothing ever waits, at the cost of a much harder mental model (monads all the way down). Teams use WebFlux when they must, not for prestige — and with virtual threads, they must less and less. Our path: blocking code + virtual threads, reactive only if we ever prove we need it.

  • Spring Boot: starters, auto-config, profiles, migrations — done, Stage 0
  • Spring MVC + validation + error handling — done, accounts service

The annotations you'll actually type

An annotation is a metadata label — @Something before a class, method, or field — that tells a framework "do something with this." You already use most of these. Grouped by where they live, one small sample each:

/* 1 — HIRING STAFF: make the container employ a class */
@Service                          /* business rules. Siblings: @Component (generic),
public class AccountService {}       @Repository (data), @RestController (web) */

/* ...and hiring things the scanner can't see: */
@Configuration
public class PayflowConfig {
    @Bean                          /* this method's return value becomes a bean */
    Clock systemClock() { return Clock.systemUTC(); }
}
/* 2 — THE WEB DESK: mapping HTTP onto methods */
@RestController
@RequestMapping("/api/accounts")          /* shared URL prefix */
public class AccountController {

    @PostMapping                            /* POST /api/accounts */
    ResponseEntity create(
            @Valid @RequestBody CreateAccountRequest request) { ... }
            /* @Valid = run the checks    @RequestBody = Jackson parses JSON into this */

    @GetMapping("/{id}")                    /* GET /api/accounts/abc-123 */
    AccountResponse get(@PathVariable UUID id) { ... }
            /* @PathVariable = that {id} piece of the path, as a UUID */
}
/* 3 — THE CONTRACT RULES: on the DTO, enforced at the door by @Valid */
public record CreateAccountRequest(
        @NotBlank String customerName,              /* not null, not whitespace */
        @Email String email,                        /* must look like an address */
        @NotNull @PositiveOrZero BigDecimal openingBalance) {}  /* >= 0 */
/* 4 — THE DATA LAYER: this class mirrors a table */
@Entity @Table(name = "accounts")
public class Account {
    @Id @GeneratedValue(strategy = GenerationType.UUID)
    private UUID id;                    /* primary key, DB generates it */

    @Enumerated(EnumType.STRING)
    private AccountStatus status;   /* store ACTIVE, not a magic number */
}
/* 5 — THE WORKHORSES: the two you'll type most in services */
@Transactional                    /* one method = one transaction: all writes commit, or none do */
public Account create(...) { ... }

@Value("${accounts.retry.max:3}")   /* read from application.yml, default 3 if absent */
private int maxRetries;

Two footnotes. @Autowired: you'll see it in older code on fields, but with a single constructor it's implicit — constructor injection without the label is the modern style we use. Coming later, when their stages arrive: @KafkaListener (a method invoked by a message), @Cacheable (skip the work if we did it recently), @Scheduled (run me at 2 AM), @PreAuthorize (only role X may call this).
