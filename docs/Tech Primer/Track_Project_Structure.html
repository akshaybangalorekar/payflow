PayFlow Track · Project Structure

Where everything lives (and why)

The monorepo map, the rules behind it, a template for new services, and five scenarios you'll actually hit.

The map
payflow/                        /* the monorepo: everything in one place */
├── services/                  /* one folder per microservice */
│   ├── accounts/              /* running today */
│   ├── transactions/          /* Stage 1 */
│   └── ...
├── docker/
│   └── compose.yml            /* the whole stack: DBs, Kafka, tools */
├── contracts/                 /* shared API truth (Stage 2): openapi/, avro/ */
├── docs/adr/                  /* architecture decision records */
├── notes/                     /* your learning notes */
└── WALKTHROUGH.md

Two organizing principles: one service per folder, and each service owns its database — only accounts' migrations ever create or change accounts tables. That ownership rule is the whole point of microservices: no other service reaches into accounts' tables, ever; they ask accounts' API instead.

Inside one service — accounts
services/accounts/
├── pom.xml                    /* this service's dependencies ONLY */
└── src/
    ├── main/
    │   ├── java/com/payflow/accounts/
    │   │   ├── AccountsApplication.java     /* the 3-line boot class */
    │   │   ├── api/                         /* HTTP layer: controllers + DTOs */
    │   │   │   ├── AccountController.java
    │   │   │   ├── GlobalExceptionHandler.java
    │   │   │   └── dto/CreateAccountRequest.java
    │   │   ├── domain/                      /* entities: what we persist */
    │   │   ├── repo/                        /* Spring Data interfaces */
    │   │   └── service/                     /* business rules + exceptions */
    │   └── resources/
    │       ├── application.yml              /* port, DB, config */
    │       └── db/migration/                /* Flyway: V1, V2, V3... forward only */
    └── test/                                 /* mirror of main/, for tests (Unit 7) */

This is package-by-layer (api / domain / repo / service): clean at our size. Larger services often switch to package-by-feature (account/, statement/ each holding its own vertical slice) — we'll revisit if any service outgrows this.

The template — starting a new service

Yes, there's a standard way, and it's not copy-paste: Spring Initializr (start.spring.io) generates a skeleton with correct versions. Settings: Maven · Java 25 · packaging Jar · dependencies: webmvc, data-jpa, validation, flyway, postgresql. Then: drop the generated folder into services/, give it the next free port (accounts=8081, transactions=8082…), and add its own Postgres + that port to docker/compose.yml. One caution, learned the hard way: Initializr and older tutorials may still generate Boot-3-era names (starter-web) — in Boot 4 it's starter-webmvc. When in doubt, read the migration guide, not the memory.

Five scenarios — where does it go?

S1"Add an endpoint: GET /api/accounts/{id}/status"

A method in AccountController (plus a service method if there's logic). No new files, no migration — the data already exists. The controller reads the account via the service and returns the status.

S2"Store the customer's phone number"

Touches four places, and never by editing V1: add the column via a new migration V2__add_phone.sql (ALTER TABLE accounts ADD COLUMN phone VARCHAR(15)), add the field to the Account entity, to CreateAccountRequest with @Pattern validation, and to any response DTO. Flyway applies V2 at next startup. Flyway's history table means V1 is written in stone — migrations only move forward.

S3"Build the notifications service"

Generate via Initializr (template above) → services/notifications → port 8085 → its own Postgres in compose → same package skeleton (api/domain/repo/service). In Stage 2 it becomes a Kafka consumer, which is why it owns its own DB for delivery-tracking state.

S4"A stack trace says com.payflow.accounts.api.AccountController:29"

Decode it mechanically: the dots are folder separators under src/main/java/ → src/main/java/com/payflow/accounts/api/AccountController.java, line 29. Every stack trace in every service follows this map — which is one reason package structure is boring and predictable on purpose.

S5"Where does the shared API contract go?"

When two services need to agree on an API (payouts calling fraud-check, or a Kafka event schema), the contract lives in contracts/ at the repo root — OpenAPI YAML for REST, Avro schemas for Kafka events (Stage 2). Shared truth lives outside any single service; nobody's service owns a contract both depend on.
